This is now an early architecture requirement.

IMPORTANT:

Catcher-specific ability
and
C position proficiency

must remain separate concepts.

Example:

A player may have excellent catcher tools but low C proficiency because they are inexperienced.

Another player may have average physical catcher tools but very high C proficiency because they are an experienced veteran.

Do not collapse these into one CatcherRating.

## Phase integration

### Phase 1

Add catcher-specific ratings to the Player/Ratings architecture.

Add explicit C proficiency separation.

Update public visibility/read-model requirements accordingly.

### Phase 2

The baseball reducer/scoring model must support catcher-relevant events and attribution required by the game.

Examples include:

- passed-ball handling
- stolen-base attempts / caught stealing
- catcher defensive participation
- catcher workload attribution

Do not incorrectly merge official wild pitch and passed ball scoring.

### Phase 3

Integrate catcher abilities into the probability resolver.

Receiving / Framing:
- may slightly affect marginal called-ball/strike outcomes where the internal pitch/count model supports it

Blocking:
- affects handling of difficult pitches and passed-ball/runner-advance risk

Pop Time:
- combines with Arm and C proficiency when resolving stolen-base attempts

Game Calling:
- provides bounded influence on pitch-selection quality / mistake suppression / pitcher execution
- must NOT directly inflate pitcher base ratings

A conceptual caught-stealing model should depend on factors such as:

catcher Arm
+ Pop Time
+ C proficiency
+ pitcher delivery/runner-control context
- runner speed / stealing skill
+ game context

Do NOT create one single "Caught Stealing Ability" rating.

### Phase 7

Catcher-specific skills and C proficiency must have proper growth/training/exposure rules.

Returning to catcher after playing another position must preserve prior C proficiency according to the existing proficiency architecture.

### Phase 8

Catcher workload must interact with fatigue and injury systems.

Catching should generally impose more physical workload than ordinary field positions.

Repeated catcher starts may temporarily reduce effective performance through fatigue.

Do not permanently reduce base ratings merely because the player caught several games.

# 8. ADD BATTERY CHEMISTRY

Add a pitcher-catcher pair relationship called:

`BatteryChemistry`

This is NOT the same thing as personal friendship.

Model it per pitcher-catcher pair.

Conceptually:

catcher_id
pitcher_id
battery_chemistry
shared_appearances
last_battery_date
other required progression metadata

Do not store one global chemistry number on the catcher.

Examples:

C001 + P001 = very high chemistry
C001 + P002 = normal chemistry
C001 + P003 = low chemistry

## Relationship separation

Personal relationship:
human/social closeness

Battery Chemistry:
baseball-specific understanding and working familiarity

They may influence each other, but must remain distinct.

High personal familiarity may modestly improve Battery Chemistry growth speed.

It must NOT automatically guarantee excellent baseball chemistry.

## Chemistry growth

Battery Chemistry may improve through:

- shared game appearances
- spring camp work
- bullpen/catching sessions where represented
- repeated seasons together
- meaningful high-pressure game experience

It may decay slowly after long periods without working together if appropriate.

Avoid excessive churn.

## Gameplay effect

Battery Chemistry must affect effective game performance only.

It must NOT permanently change base ratings.

Possible bounded effects:

- fewer sign/communication mistakes
- slightly improved receiving consistency
- slightly improved blocking decisions
- better use of catcher Game Calling
- pitcher comfort / execution stability
- better situational coordination

Do NOT implement:

Battery Chemistry 90
→ pitcher Stuff +10

or similar direct permanent rating inflation.

# 12. REVISE THE GENERATIVE AI PHILOSOPHY

This is an important owner decision.

The philosophy is NOT:

"use AI as little as possible."

The philosophy is:

Use generative AI where it significantly increases immersion,
personality, expression, and narrative variety.

Do not use generative AI where normal deterministic/rule-based code
is more appropriate, more reliable, or provides no meaningful benefit.

In short:

Do not use AI merely because AI can do the task.

Use AI aggressively where AI makes Star Player substantially more immersive.

## Generative AI should NOT own:

- game results
- baseball simulation
- player growth
- aging
- injury outcomes
- lineup decisions
- manager/team operations
- draft outcomes
- contracts
- FA outcomes
- trades
- generated-player ratings
- league progression
- authoritative relationship values
- authoritative game facts

These remain C# Game Core / deterministic or seeded game systems.

## Generative AI should be actively used for:

- free-text player interviews
- contextual fan reactions
- SNS / community reactions
- selected high-value narrative articles
- other high-value expressive narrative where approved

Routine information that does not gain much from AI should remain template/procedural.

Example:

ordinary 4-for-1 game
→ no need for expensive AI content

career first home run / MVP / Korean Series Game 7 / major controversy
→ AI content is valuable
