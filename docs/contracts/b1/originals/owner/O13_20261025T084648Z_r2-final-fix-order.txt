Star Player — B1 T11 R2 잔여 결함 최종 수정
OWNER 작업 지시
Codex T11 표적 재검수 결과는 FIX_REQUIRED다.
R1·R3·R4는 RESOLVED이므로 재설계하지 않는다.
이번 작업 범위는 R2의 두 잔여 결함으로 한정한다.

* R2-A: INPUT_BUNDLE의 실제 소비 입력 완전성
* R2-B: PREFLIGHT의 필요한 기록 보존·검증

1. TASK 파일 작성 및 작업 재개 기준
먼저 다음 파일을 작성한다.
`docs/tasks/B1_T11_R2_FINAL_FIX_TASK.md`
이번 지시 전체와 다음 내용을 포함한다.

* Codex R2-A·R2-B 원문 지적
* 승인 계약 §21 관련 조항
* 실제 소비 입력과 Preflight 기록의 출처
* 수정 대상 코드·함수·테스트
* Red/Green 반례
* 기존 해결 사항의 회귀 조건
* 최종 수용 기준
* 중단 후 새 세션 재개 방법

루트 TASK.md는 D3 보호 파일이므로 절대 수정하지 않는다.
TASK를 작성한 뒤 해당 파일을 기준으로 이번 승인 범위의 구현과 테스트를 이어서 수행한다.
진행 상황은 기존 구현 로그에 남긴다.
2. R2-A — INPUT_BUNDLE 수정
현재 Environment Profile·PZL Test Profile 두 항목으로 고정한 입력 목록 검사를 제거한다.
먼저 실제 Production 및 독립 검증 경로에서 소비하는 입력 파일을 전수 조사한다.
특히 다음 경로를 확인한다.

* HarnessData.LoadTuningV4
* HarnessData.LoadRules
* SimHarness.csproj의 EmbeddedResource
* 게임 실행·Replay·평가 과정의 추가 입력 로딩
* 승인된 실행 계획 및 Build Provenance와의 연결

환경·시험 프로필 두 개가 실제 전체 입력 집합이라고 가정하지 않는다.
필수 INPUT_BUNDLE 집합은 제출자의 자기 선언이 아니라, 신뢰된 승인 계획·빌드 정보·실제 입력 로딩 경로를 통해 도출해야 한다.
각 입력에 대해 다음을 확인한다.

1. 논리적 입력 식별자와 실제 파일 또는 EmbeddedResource의 대응
2. 원본 바이트 및 Raw SHA
3. 실제 실행에서 소비된 바이트와 보존 원본의 동일성
4. Archive Snapshot, ArtifactRef, RAW_INVENTORY, Receipt SourceFiles 결속
5. 승인된 버전·Pin·Build Provenance와의 정합성
6. 중복·누락·치환·임의 추가 입력의 거부

EmbeddedResource로 포함된 튜닝·규칙 데이터는 빌드 시 원본과 런타임에서 실제 소비한 리소스 바이트의 관계를 검증한다.
기존 의미 Hash나 Build Provenance에 입력 정보가 포함되어 있다는 이유로 Raw 원본 보존을 생략하지 않는다.
3. R2-B — PREFLIGHT 수정
모든 PREFLIGHT의 기대 개수를 0으로 고정하고 참조를 일괄 거부하는 코드를 제거한다.
실제 Family·Unit 실행에서 필요한 Preflight 기록을 조사한다.
특히 기존 PreflightReport.Checks, Unit Manifest, Family/Dominance 색인, Preflight 수행 시점과 실패 기록을 확인한다.
다음 요구를 충족한다.

* 필요한 Family·Unit Preflight 기록을 빠짐없이 보존
* 최초 경기 전에 생성된 실제 Preflight 결과와 결속
* 단순 Attestation 존재만으로 Preflight 보존을 인정하지 않음
* DIAGNOSTICS 집계만으로 필수 PREFLIGHT를 대체하지 않음
* 원본 기록의 출처·범위·바이트·SHA를 확인
* Archive Snapshot 및 Receipt SourceFiles에 결속
* 독립 검증에서 실제 Preflight 결과와 비교
* 누락·다른 Unit 혼합·변조·중복 시 Fail-Closed

기존 파일 내부에 보존하는 방식을 택한다면 PREFLIGHT 역할·원본 바이트 범위 및 해당 기록 위치를 검증 가능하게 연결한다.
기존 규범과 양립하는 보존 구현을 우선한다.
새로운 공개 형식이나 정책 결정이 불가피하다면 임의로 규범을 추가하지 말고 해당 사항만 OWNER_DECISION_REQUIRED로 분리한다.
4. 필수 반례 및 양성 시험
R2-A:

* 프로필 두 개만 있고 튜닝·규칙 입력이 빠진 경우 거부
* 실제 소비 입력이 모두 보존된 경우 통과
* 소비 입력 하나 누락
* Raw SHA 불일치
* 동일 식별자의 다른 바이트
* EmbeddedResource와 원본 파일 불일치
* 승인 집합과 다른 입력 추가
* Inventory와 SourceFiles 양쪽에서 동일 원본을 제거한 경우 거부

R2-B:

* 필수 PREFLIGHT 0개인 경우 거부
* 정상 Family·Unit별 Preflight 기록 보존 통과
* 특정 Unit의 Preflight 누락
* 다른 Unit의 Preflight 대체
* Preflight 내용 및 SHA 변조
* Attestation만 존재하는 경우 거부
* DIAGNOSTICS만 존재하는 경우 거부
* 유효한 Preflight의 원본·Inventory·Receipt 결속 통과

Phase:

* 정상 Calibration·Integration·Dominance 영수증 발급
* 실제 필수 ORIGINAL 전체를 포함한 Phase 영수증 발급
* 공유 ORIGINAL은 정해진 동일성 조건에서만 병합
* 누락된 Family 원본·INPUT_BUNDLE·PREFLIGHT를 Phase 발급 시에도 거부
