## 1. R1 — 검증 결과 불변 스냅샷

기존 결함: 검증된 동일 객체의 공개 byte[]·SourceFiles·중첩 JSON을 발급 전에 변경하면 검증 결과 A+와 보존된 원본이 불일치할 수 있었다.

확인할 사항:

- 내부 검증 스냅샷이 외부 수정으로 변경되지 않는가?
- Canonical 바이트, A+, SourceFiles, Inventory가 동일한 검증 사실에 결속되는가?
- 같은 객체의 내부 배열·컬렉션·중첩 JSON 변경도 안전한가?
- 정상 인증 발급 경로는 여전히 동작하는가?

수정 전 실패·수정 후 성공 증거와 실제 코드를 대조한다.

## 2. R2 — 필수 ORIGINAL 증거 완전성

기존 결함: 승인 기록·Build Provenance 등 필수 원본이 Archive와 Inventory 양쪽에서 함께 빠져도 인증이 가능했다.

확인할 사항:

- §21의 필수 역할과 개수를 신뢰된 실제 입력에서 도출하는가?
- APPROVAL_RECORD·BUILD_PROVENANCE·INPUT_BUNDLE·필요 PREFLIGHT·REGRESSION_PROOF 등을 누락하면 거부하는가?
- 실제 검증에 사용한 원본 바이트와 SourceFiles·Inventory가 일치하는가?
- 제출 목록과 Inventory가 똑같이 불완전한 경우도 거부하는가?

추가 중점:

- 신규 `simharness-regression-proof-v1`이 기존 승인 계약을 만족하는 구현 형식인지, 별도 OWNER 규범 승인이 필요한지 확인한다.
- INPUT_BUNDLE 범위를 Environment Profile과 PZL Test Profile로 제한한 선택이 실제 소비 입력 파일 보존 의무와 일치하는지 검토한다.
- 두 프로필이 다른 승인·입력 역할과 중복되거나, 실제 Run 입력이 누락되지 않았는지 확인한다.

## 3. R3 — Phase 원본 합집합

기존 결함: 서로 다른 Family 원본이 같은 artifact_id를 사용했고, GroupBy 후 첫 원본만 남기는 방식으로 다른 원본이 삭제됐다.

확인할 사항:

- Calibration·Integration·Dominance의 서로 다른 원본이 모두 보존되는가?
- 동일 validation-set 공통 원본은 허용된 조건에서 정확히 한 번만 포함되는가?
- 동일 Artifact ID가 다른 경로·SHA를 가리킬 때 조용히 제거하지 않고 거부하는가?
- Phase Inventory와 영수증 source_files에 모든 필수 ORIGINAL이 남는가?

정상 세 Family의 영수증을 발급하고 Phase 영수증까지 도달하는 실제 양성 시험을 확인한다.

## 4. R4 — Archive 루트 생성 경계

기존 결함: Directory.CreateDirectory(root)가 PinnedDirectory 검증보다 먼저 수행돼, Junction을 거쳐 승인 루트 밖에 디렉터리를 생성할 수 있었다.

확인할 사항:

- 루트 생성 이전에 부모 경로의 신뢰성을 확보하는가?
- Junction·Reparse Point 경로에서 외부 디렉터리 생성이 발생하지 않는가?
- 루트 생성과 파일 쓰기 사이에 경로 교체 가능성이 남는가?
- 정상 보호 경로에서 생성·읽기·재시도는 가능한가?

수정 전 공격 재현과 수정 후 거부 시험을 비교한다.

## 7. 수행 제한

READ-ONLY로 진행한다.

코드, 문서, TASK, Git 상태를 변경하지 않는다. Stage·Commit·Push 금지.

명령 실행이 파일 생성·수정을 수반한다면 임의 실행하지 않는다.

승인 계약과 OWNER 결정 원문을 수정하지 않는다.

실제 실행하지 않은 시험을 직접 실행한 PASS로 표시하지 않는다.
