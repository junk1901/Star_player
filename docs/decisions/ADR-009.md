## The problem (N-04)

`SeedManifest.AfterGames` (FC-D5.3) lets a calibration run end at a block boundary once the cumulative PA target is reached, so the games actually run can be only the leading blocks of the approved seed file. The F-C2-A replay contract assumes the opposite. Four consequences were identified in the design review; all four are resolved by the decisions below:

| # | Where (F-C2-A, HEAD `02e75cf`) | Consequence if a stopped run were recorded as a prefix |
|---|---|---|
| 1 | `OfficialReplay.VerifyAgainstSeedFile` | the exact list comparison against the approved seed file fails (`Replay.seed_games_mismatch`) |
| 2 | `OfficialPreflight` builds `attestation.config_hash` over the whole seed list; `OfficialReplay.Verify` compares it with the manifest's `config_hash` | a prefix would change `run.config_hash` and fail `Replay.attestation_config_mismatch` before consequence 1 is reached |
| 3 | `SimRunner.RunSpecs` plays every given game | a replay of the full recorded list would run past the stop and could not match the result hash |
| 4 | `RunResult.AllCompleted` / `Program.ExitCodeOf` | a legitimate early stop would be reported as an incomplete run (exit 1) |

## Decisions

Mapping to the owner's identifiers: SR-D1 = D-1, SR-D2 = D-2, SR-D3 = D-3, SR-D4 = D-4, SR-D5 = D-5, SR-D6 = D-6, SR-D7 = condition A, SR-D8 = condition B, SR-D9 = condition C.

### SR-D1 — Calibration stop rule (Option B)

1. **The approved plan is the whole seed file.** The Seed Manifest whose raw-file SHA-256 is pinned outside the file (F-C2-A reader contract) is the complete execution plan. The manifest of a run keeps `games` equal to that whole approved list, in file order, always; a stopped run records its plan, never its prefix. The exact-list comparison of F-C2-A (`Replay.seed_games_mismatch`) therefore stays as it is, and `RunConfig.ConfigHash` over the whole list stays equal to `attestation.config_hash`.
2. **The run ends at the first legal stop point.** Games run in file order, one block of `block_size_games` at a time. After each completed block (and only then) let `n` be the number of games run (a failed game counts as run) and `PA` the cumulative valid PA (SR-D3.2). The run ends at the first block boundary at which:
   - `PA ≥ pa_target` → stop reason `TARGET_REACHED`; or, if that does not hold,
   - `n` equals the number of seeds → stop reason `SEEDS_EXHAUSTED`.
   The target is tested before exhaustion, so `SEEDS_EXHAUSTED` always means `PA < pa_target`. A block in progress is always completed (FC-D5.3); a target reached mid-block changes nothing until that block ends. This is exactly the committed `SeedManifest.AfterGames` behavior and is not a new rule.
3. **The stop point is unique.** There is no choice of prefix: no earlier stop, no later stop, no skipped, reordered, substituted or added seed is legal. A seed after the stop point is **not executed** (its outcome is never observed by the official run); it is not "excluded after seeing results", so FC-D5.2 holds.
4. **Replay re-derives the stop point** with the same rule and never trusts a recorded prefix (SR-D8). The existing `AfterGames` function is the rule's definition; any stop-aware executor and any replay must use one shared implementation of it.
5. The stop parameters (`block_size_games`, `pa_target`, the seed count) are read from the externally pinned seed file only (SR-D8.2).

### SR-D2 — Document authority

This ADR is the normative contract for the stop rule, the stop record, the `run-result-v2` binding and the replay derivation. ADR-008 remains the normative policy; FC-D5.3's "pre-declared blocks / complete the block in progress" is refined here, not replaced. `ROADMAP.md` 3-F, `docs/game-engine.md` section 35 / 36 and `docs/SYSTEM_CONTRACTS.md` keep pointing to ADR-008; they are not edited by this freeze, and a pointer to this ADR is a documentation follow-up (see "Open items").

### SR-D3 — Game failure, cancellation and integrity

1. **A failed game is never hidden or replaced.** It stays in the run result with its `game_id`, `seed`, status, `error_code` and hashes; the next seed in the plan is never substituted (FC-D5.2, FC-D9.2).
2. **Only valid PA counts.** `cumulative_pa` is the sum of plate appearances of **Completed** games whose event-derived statistics agreed with the BoxScore cross-check (the `GameExecutor` rule). The PA of a Failed or Cancelled game is not included. A failed game still counts as a game run for block progress (`n`), so the block grid does not move.
3. **An engine-level failure of one game does not end the run.** The run continues exactly by the plan and the stop rule (a failed game can delay `TARGET_REACHED` because its PA is not counted). A run with at least one failed game is never a statistical PASS (SR-D9). If such a run still reaches a stop point by the rule, it terminated by the rule: its stop record (SR-D7) is written and preserved as evidence, and the gate is `FAIL` (SR-D9); failures never turn the run into an aborted one.
4. **Fail-closed integrity.** If the trust in the inputs, the evidence or the execution environment is damaged — a failed preflight check, a pin or hash mismatch, a pin check that fails in the middle of a run, a tampered or unreadable seed file, an unreproducible environment fact required by FC-D10 — the run is refused before it starts (the existing Official preflight refusal), or, if detected after it started, it is aborted without a stop record. Such a run cannot yield PASS and is never accepted by an official replay as a normal termination. Reproduction evidence is preserved (FC-D10, FC-D11).
5. **A cancelled run is not a termination.** A run cancelled at any point has no stop record, is not a replay-eligible result, and must not be presented as `TARGET_REACHED` or `SEEDS_EXHAUSTED`.
6. The exact run-status labels and error codes for these cases are specified in F-C2-B on top of the existing vocabulary (`COMPLETED`, `GAMES_FAILED`, `METRICS_ERROR`, `Official.*`, `Replay.*`, exit codes 0 / 1 / 2 / 3); this ADR fixes the meaning, not the spelling. No new process exit code may mean success.

### SR-D4 — Dry run

1. `fc2-dry` may be used to integration-test the stop rule with a **small positive** `pa_target`. This needs a reader change (F-C2-B): today only `fc3-cal` may declare a target.
2. The official floor stays: an official `fc3-cal` manifest must declare `pa_target ≥ 100,000` (FC-D7.1, `SeedManifestReader.CalibrationMinPa`).
3. Dry-run results are diagnostic. They are never official calibration statistics, never carry an official envelope, and are never accepted by official replay or by any gate.
4. Official and dry seeds are distinguished by family, competition-key namespace (`fc3-*` / `fc2-dry*`), seed file and pin. Whether their numeric seed values must also be disjoint is **not decided here** (the RNG context includes the `GameId`, so equal numbers in different namespaces are different streams); it is left to the Final Execution Freeze.
5. `fc2-dry` is not promoted to an official family; `FamilyCohorts`, `SeedFamilies.IsOfficialCompetitionKey` and the official envelope rules do not change.

### SR-D5 — Scope by family

The stop rule is an official calibration rule: it applies to **`fc3-cal` only**. `fc3-int` (exactly 100 games, FC-D7.2), `fc3-dom` (strategy matrix) and every future official family keep the existing full-execution contract: no `pa_target`, no stop record, exact whole-list comparison. `fc2-dry` is the single exception path of SR-D4. A stop-aware result for a family other than `fc3-cal` (or `fc2-dry`) is refused.

### SR-D6 — `MaxGames`

An official seed manifest (`fc3-cal`, `fc3-int`, `fc3-dom`) must declare `max_games == number of seeds`. `max_games` is then the declared cap and the plan length at the same time, and no unused cap slack exists in an official file. `fc2-dry` is not required to follow this rule. This tightens the F-C2-A reader, which today accepts `seeds ≤ max_games` (`Seed.cap_exceeded` only rejects more seeds than the cap); the tightening and the tests that rely on slack are F-C2-B work. The other F-C2-A seed rules (whole blocks, `max_games % block_size == 0`, indices `1..n`, GameId rule) are unchanged.

### SR-D7 — Stop record, versions and backward compatibility

1. **Stop record.** A stop-aware result carries `results.stop`:

   | Field | Meaning |
   |---|---|
   | `executed_games` | number of games run; a multiple of `block_size`; the first `executed_games` entries of `games` were run, in order |
   | `stop_reason` | `TARGET_REACHED` or `SEEDS_EXHAUSTED` (no other value) |
   | `cumulative_pa` | the valid PA of SR-D3.2 at the stop point |
   | `block_size` | the pinned seed file's `block_size_games` |

2. **Required for stop-aware v2.** A stop-aware (v2) result must carry it, and its absence is a refusal, not a default. It is written exactly when the run terminated by the rule; SR-D3.4 / SR-D3.5 runs write none and are not v2 results.
3. **`run-result-v2` is introduced separately.** Its hash text binds, at least: the unchanged `ConfigHash` over the whole plan, the four stop fields, the result hash of every executed game in plan order, and the aggregate counters. The exact byte layout is fixed in F-C2-B and covered by a golden vector before first use. `run-result-v1` text and hash are not changed and keep serving legacy and non-stop-aware runs.
4. **No downgrade by self-declaration.** Which version is required follows from trusted inputs, not from the manifest: for an official `fc3-cal` replay, the pinned seed file's family requires v2 and a stop record. A manifest that drops `results.stop` or presents v1 to avoid the stop check is refused (consistent with the F-C2-A rule that the competition key, mode and envelope must agree; `Replay.official_envelope_missing` / `Replay.official_mode_mismatch` are unchanged). The manifest field that names the result version is a F-C2-B detail.
5. **Legacy.** v1 / legacy manifests and fixtures (`legacy-manifest-neutral-default`, `legacy-manifest-automated-v1`) replay as before with the same hashes. The legacy `run` / `replay` smoke paths and `mode != official` runs are unchanged.
6. `OfficialAttestation` v1 is unchanged: its `config_hash` is the whole-plan hash, the stop parameters are covered transitively by `seed_manifest_sha256`, and the attestation is still created before the run.

### SR-D8 — Replay integrity

1. **Recomputed, not trusted.** An official `fc3-cal` replay re-derives from the approved seed file and the replayed game results: the number and order of games run, the first legal stop point, `cumulative_pa`, `block_size`, `stop_reason` and the result hash (`run-result-v2`). It re-runs only the derived games, in plan order.
2. **Parameters from the pin.** `block_size`, `pa_target` and the plan come from the externally pinned seed file (the same read as `VerifyAgainstSeedFile`); never from `results.stop`.
3. **Recorded values are only compared.** `results.stop` and the recorded `plate_appearances` (and every other recorded count) are never sufficient for PASS: a replay matches only if every derived value equals the recorded one **and** the recomputed `run-result-v2` equals the recorded `run_result_hash`.
4. **What a replay must refuse** (code spelling in F-C2-B): a missing or malformed stop record; `executed_games`, `stop_reason`, `cumulative_pa` or `block_size` different from the derived value; an earlier stop, a later stop, a skipped, replaced, reordered or added seed; `results.games` that is not the leading run of `games`; a cancelled or aborted run presented as terminated; a v1 result for `fc3-cal`; a `games` list that is not exactly the approved whole plan.
5. **Failures reproduce.** A replay of a run that contains failed games reproduces them (the result hash includes the failure code), as reproduction evidence; it never turns the run into a PASS.
6. **Stop-aware replay of `fc2-dry`.** A dry run has no official pin or envelope. Where a dry-run replay obtains its trusted stop parameters is a F-C2-B design item (see "Open items"); whatever is chosen must not weaken any official check and must keep SR-D4.3.

### SR-D9 — Technical success versus the statistical gate

1. **Two separate axes** (FC-D10): the technical outcome of the process (exit code, run status) and the statistical gate (`NOT_EVALUATED`, `INSUFFICIENT_SAMPLE`, `PASS`, `FAIL`). Exit 0 is never a PASS.
2. **Outcome table** (labels per SR-D3.6; the gate follows FC-D6 / FC-D9):

   | Situation | Technical outcome | Gate |
   |---|---|---|
   | `TARGET_REACHED`, no failed game, metrics computed | success (exit 0) | decided by FC-D6 statistics (may be `PASS` or `FAIL`) |
   | `SEEDS_EXHAUSTED` (so `cumulative_pa < pa_target`), no failed game, metrics computed | success (exit 0): the plan ran as declared | `INSUFFICIENT_SAMPLE`; no seed is added |
   | terminated by the rule, at least one failed game | not success (existing "games failed" exit 1) | `FAIL` (FC-D9.1); never `PASS` |
   | terminated by the rule, metrics could not be computed | not success (existing metrics-error exit 3) | `NOT_EVALUATED` |
   | cancelled (SR-D3.5) | not success | `NOT_EVALUATED` |
   | integrity or environment trust damaged (SR-D3.4) | refused or aborted, never exit 0 | `NOT_EVALUATED` |
3. `stop_reason` states why the run ended; it is never a gate verdict. `SEEDS_EXHAUSTED` is a normal termination (technical success if nothing else failed) and `INSUFFICIENT_SAMPLE` is the gate verdict that follows from `cumulative_pa < pa_target` (FC-D9.4); a failed game turns the verdict into `FAIL` regardless of the stop reason, and a cancelled or aborted run has no stop reason at all.
4. `RunResult.AllCompleted`, `Succeeded` and `Program.ExitCodeOf` must mean "every game the stop rule required was run and Completed" for a stop-aware run; their meaning for legacy and non-stop-aware runs does not change.
5. An early stop with `TARGET_REACHED` does not by itself make the sample sufficient for every metric: the FC-D6 minimum denominators and stratum minimums (F1, F8) are still checked by the evaluator, and a missed minimum is `INSUFFICIENT_SAMPLE` for that metric.
6. FC-D12 is unchanged: CLI exit 0 alone never passes the 3-F gate.

## Notes and open items

- **Gaps in the current code (informational; not changed by this freeze):** the reader rejects `pa_target` outside `fc3-cal` (SR-D4.1) and accepts `seeds ≤ max_games` (SR-D6); `SeedManifest.AfterGames` is not called by any runner yet; `SimRunner.RunSpecs` runs every given game; `RunResult.AllCompleted` compares with `Requested`; `OfficialApprovals.Current` is still all-unfrozen. All are F-C2-B work.
- **Open (F-C2-B design, must not weaken SR-D8):** the trusted source of stop parameters for a `fc2-dry` replay (SR-D8.6), the manifest field that names the result version (SR-D7.4), the byte layout of `run-result-v2` (SR-D7.3), the run-status labels and error codes (SR-D3.6), and whether the small `fc2-dry` target has a stated upper bound.
- **Open (Final Execution Freeze):** numeric disjointness of official and dry seeds (SR-D4.4); block size and cap; seed lists and pins.
- **Residual risk the replay cannot remove:** an operator can run privately and publish only a preferred official attempt. This is a process control (every official attempt keeps its evidence, new output directories only, FC-D9.5, FC-D10, FC-D11), not a replay property, and should be stated in the Final Execution Freeze.
- **Statistical note:** stopping at a cumulative PA target is a deterministic, pre-declared data-dependent stopping rule. The overshoot is at most one block (about 500 PA for a 7-game block, ~0.5% of 100,000), which is negligible against the DEFF = 2 design assumption of FC-D6; it is accepted by the existing FC-D5.3 block rule and recorded here so it is not rediscovered later.
