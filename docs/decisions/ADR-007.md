## Decisions (3-C1)

1. **Optional trailing `PitchLocation? Location = null`.** Added as the last constructor parameter of `PitchSpec` (used by `PitchEvent` and `TakeEvent`) and of `InPlayEvent`. Existing argument order and defaults are unchanged; every existing call site, fixture and JSON file compiles and reads as before. A Phase 2 event has no location: that is legacy data, never inferred or backfilled. The Phase 3 resolver (3-C2) must always supply one for an actual pitch; the type itself keeps it optional because legacy events must stay representable. The reducer does not require it in 3-C1 (it does not know the resolver's mode) — the requirement for new data lives in the format-2 reader and writer and in the resolver.
2. **`PitchLocation` is reused as is.** Its factory already enforces the zone model version, a known zone id, a defined applied side and a boundary class equal to the model's class for the zone; the record has a private constructor and no init setters, so no unvalidated location can exist. Batter-relative inside/outside is unchanged. The pitcher's `TargetZone` is a different type and cannot be passed here.
3. **An `InPlayEvent` is its own pitch.** Its `Location` is the location of that one pitch; no `PitchEvent` is added before it, and `GameReducer` counting is untouched (test: identical stats and pitch totals with and without locations over a sequence ending in an in-play event).
4. **`ef1` is untouched; `ef2` identifies only events that carry a location.** `EventFingerprint.Version` stays `"ef1"` and means what it meant. New `VersionV2 = "ef2"`. `VersionOf(event)` is `ef2` for a `PitchEvent` / `TakeEvent` / `InPlayEvent` with a location and `ef1` for everything else (legacy pitches without a location, `ApproachEvent`, `RunnerPlayEvent`, `SubstitutionEvent`). A receipt is never converted from one version to the other.
5. **`ef2` canonical text.** `ef2|kind|` + exactly the `ef1` field list of the event (same order, escaping, enum names, set rules) + `|zone_model=…|zone=…|side=…|boundary=…` in that fixed order. Example: `ef2|pitch|spec={Ball;None;[];None;~}|zone_model=pzl-zones-v1|zone=in.r2c2|side=Right|boundary=Clear`. Hashing is the same lower-case SHA-256 of the UTF-8 text. The event id is not part of the text. Tests pin literal texts and independently computed hashes, that the `ef2` text is the `ef1` text plus the suffix for every kind, and that a change of zone or side changes the hash for every kind (boundary class is derived from the zone and cannot vary alone: building a mismatching location is refused).
6. **Receipt comparison needed no new code.** `GameReducer.Apply` already compares the stored receipt's version first: different version → `Game.event_fingerprint_version_mismatch`; same version, different kind or fingerprint → `Game.event_id_conflict`; equal → duplicate. With the version now derived from the location, the required cases follow: an `ef1` receipt re-delivered with a location added → version mismatch; an `ef2` receipt re-delivered with the location removed → version mismatch; same `ef2` event → duplicate; another zone or side, other pitch content or another kind under the same id → conflict. The correction of an inaccurate sentence (below) belongs here: an `ef1` receipt cannot "arrive with its location removed", because it never had one.
7. **Event JSON format 2 is a separate path.** `{"format_version": 2, "events": [...]}`, read by `ScriptedGameJson.ReadEventsV2` through its own DTO (`EventV2Dto` = the legacy event DTO plus `location`; `EventDto` was unsealed for this). Each pitch-bearing event (`pitch`, `take`, `in_play`) must carry `location: {zone_model, zone, side, boundary}` (snake_case enum texts); the reader rebuilds it through `PitchLocation.Create`, so an unsupported model, unknown zone, bad side, bad boundary text or a boundary that is not the zone's class is an error, never corrected. A missing or `null` location is `Fixture.location_missing`; a location on a non-pitch event is `Fixture.location_unexpected` (no fake location is required of or accepted on `approach` / `runner_play` / `substitution`). Wrong `format_version`, a bare array, unknown members and missing required members are errors. An explicit `null` for `events` or for an element of it is `Fixture.field_missing` naming `events` / `events[i]` (fix round after the Codex `CHANGES REQUIRED`, Medium: `required` accepts an explicit null, so the reader checks it itself); the whole read fails, nothing is skipped or defaulted. The same holds for a null element inside an event's own lists (`moves`, a move's `credits`, `strikeout_credits`, `batter_credits`, `errors`) and for a null `events` list or element of a scripted game or a legacy array: `Fixture.field_missing` with the exact path (second fix round, after the GPT Chat review). An optional list that is itself null stays legal with its old meaning (`strikeout_credits: null` = default catcher putout, never an empty list).
8. **Legacy stays legacy.** `ReadEvents` (bare array) and the scripted-game `format_version: 1` reader keep their DTO, so a `location` member is still an unknown member (`Fixture.json_invalid`); they never create a location and never promote data to `ef2`. `ReadEvents` now answers a version-2 envelope with `Fixture.version_unsupported` instead of a generic JSON error. The 100-game corpus pins prove the unchanged behaviour: the SHA-256 over all 30,974 `ef1` receipts and over the bytes of `WriteEvents` for the 100 games are the values computed on the unchanged 3-B2 commit `ddbc999`.
9. **Writers cannot lose a location.** `WriteEvents` (legacy) refuses any event that has a location (`Fixture.location_requires_v2`, naming the event) instead of writing JSON without it. `WriteEventsV2` refuses a pitch-bearing event without a location (`Fixture.location_missing`), so no new output lacks one. There is no silent format choice; the caller picks the path.
10. **Receipts JSON** (`EventReceiptJson`) already carries `fingerprint_version` per receipt; ef1 and ef2 receipts mix in one list and round-trip unchanged (test).

## Correction of two inaccurate sentences (no contract changed)

ROADMAP §1.14 ("Events and fingerprint compatibility") and SYSTEM_CONTRACTS C08 said that an incoming event whose id already has an `ef1` receipt "arrives with its location removed or altered" and is rejected. An `ef1` receipt belongs to an event that never had a location, so the accurate statement is: an `ef1` receipt re-delivered with a location **added** is a version mismatch, and an `ef2` receipt re-delivered with its location **removed** is a version mismatch; an altered `ef2` location is a content conflict. Both documents were edited to say this. The rejection rule and the `ef1`/`ef2` coexistence were not changed.

## Decisions (3-C2A) — single-pitch probability branch (Accepted 2026-10-11; 3-C2A only)

Code: `src/StarPlayer.Simulation/Baseball/PitchBranchDraft.cs` and `PitchBranchResolver.cs`; the stream `GameRngStreams.Target` in `Randomness/RngStreamId.cs`. Contract text: `docs/game-engine.md` section 21; report: `docs/reports/PHASE_3C2A_REPORT.md`. Nothing in `GameEvents.cs`, `GameReducer`, `EventFingerprint`, the event JSON, the tuning numbers, the rule profiles, the probability model or the RNG algorithm changed.

1. **Scope.** 3-C2A draws one pitch's categorical branch and stops. The result (`PitchBranchDraft`) is not a `GameEvent`, has no id or fingerprint, is never given to `GameReducer.Apply` and never becomes a `GameState`. Tests keep the two apart (the draft is not a `GameEvent`; the resolver source does not mention the reducer, fingerprints or `InPlayEvent`).
2. **Target zone is sampled.** `target_zone` is a probability stage whose condition is the pitcher's intent, `balanced` / `attack` / `careful` (`PitchIntent`), an explicit input. Nothing picks an intent from a hidden tendency or any hidden value; weakness-exploiting AI stays deferred (ROADMAP §1.14).
3. **New stream `game/target@1`** (ADR-004 item 20): one `NextBounded(1,000,000)` per actual pitch, before the location draw. `game/location@1` and `game/ai@1` keep their meaning.
4. **Order and streams** (every decision is exactly one `NextBounded(1,000,000)` call; raw draws may be higher):

| Stage | Stream | Reached when |
|---|---|---|
| `target_zone` (condition: intent) | `game/target@1` | every pitch |
| `actual_location` (condition: target zone) | `game/location@1` | every pitch |
| `batter_decision` (condition: actual zone) | `game/pitch@1` | every pitch |
| `called_pitch` (condition: `<mode>:<actual zone>`) | `game/pitch@1` | decision `take`, or an explicit Take that was not a hit by pitch |
| `swing_result` (condition: actual zone) | `game/contact@1` | decision `swing` in a normal pitch |
| `batted_ball` (condition: `heart` / `edge` / `outside`) | `game/contact@1` | swing result `in_play` |
| `defense_result` (condition: batted-ball type) | `game/field@1` | a batted ball exists |
| `advancement` | `game/runner@1` | **not drawn here** (3-C2B) |

   A stage that is not reached draws nothing. A reached stage whose distribution is 0% / 100% in some outcome is still drawn (`called_pitch` under `automated` is 100% strike inside and 100% ball outside; the call and its roll are recorded). `Distribution.Select` maps the roll; `StageProbability.Compute` is called with neutral inputs and no tendency (the result is the baseline row itself, pinned by a test), so no Phase 3-D / 3-E effect is switched on.
5. **Actual location.** Drawn right after the target and before the batter decision, from the row of the chosen target zone, and built only through `PitchLocation.FromZone(model, zone, side)`. `TargetZone` and `PitchLocation` stay different types. No coordinate, no new strike-zone rule.
6. **Switch hitters.** Right → Right, Left → Left, Switch → the side opposite the pitcher's throwing hand (right-handed pitcher: Left; left-handed pitcher: Right). The side is recomputed for every pitch from the caller's current pitcher hand, so a pitching change changes the next pitch's side and the same pitcher keeps the same policy. `AppliedBatterSideRules.Validate` is called on the result. The decision uses no RNG (a test proves identical draws and next position for a switch hitter and a right-handed batter, against either hand). A missing batter side or pitcher hand (`BattingSide?` / `ThrowingHand?`) is an error, never a default; the pitcher hand is required for every batter, not only for a switch hitter.
7. **Explicit `Take`** keeps the reducer's accepted outcomes (ball, called strike, hit by pitch): after the location, `batter_decision` is drawn once with the ordinary distribution, so the baseline hit-by-pitch mass is kept and no Take-only table exists. `hit_by_pitch` is a HitByPitch; `take` or `swing` is watching, so `called_pitch` is drawn once; `swing_result`, `batted_ball` and `defense_result` are never drawn. A Take is legal only at `PaStage.Start` / `Decision`, a normal pitch only at `InSequence` (the reducer's own rule, checked up front as `PitchBranch.take_not_legal` / `PitchBranch.pitch_not_legal`). Automatic plate-appearance progression is 3-C3.
8. **Validation before the first draw** (each its own error code, none corrected to success): request, state and tuning present; game in progress; Take / pitch legal for the stage; the rules declare a called-pitch mode (a `gamerules-v1` profile is never read as Automated: `PitchBranch.called_pitch_mode_undeclared`); the rules' zone model equals the tuning's (`PitchBranch.zone_model_mismatch`) and is supported; the probability-model and tuning versions are supported and the content hash is 64 lower-case hex; the intent is defined; the batter side and pitcher hand are present and defined; the snapshot restores (`GameRandom.Restore` codes pass through: `Rng.snapshot_missing`, `Rng.snapshot_format_unsupported`, `Rng.algorithm_unsupported`, `Rng.state_mismatch`, ...).
9. **No side effects.** The caller's `GameRandomSnapshot` (immutable) is restored into a private `GameRandom` that continues from that position (never reseeded); on failure or cancellation it is dropped. The `GameState` is only read. A `CancellationToken` is accepted and checked before and between decisions (`OperationCanceledException`, nothing changed). The draft carries the NEXT snapshot; the caller adopts it only if it accepts the draft. The same input gives the same draft (tested).
10. **Draft content** (resolver-internal): contract version `pitch-branch-v1`, intent, explicit-Take flag, target zone, actual location (with applied side and boundary class), `PitchBranchKind` (`HitByPitch`, `CalledBall`, `CalledStrike`, `SwingingStrike`, `Foul`, `InPlay`), the decision / called pitch / swing result / batted ball / defence result texts, the ordered steps (stage, condition, outcome, stream, exact roll, raw draws, `ProbabilityTrace`), the number of `NextBounded` calls, calls and raw draws per stream, the next RNG snapshot, the probability-model version, tuning version and content hash, and the rules profile id / version / hash. The draft and step types may not appear in an Application or Infrastructure signature (`HiddenTendencyBoundaryTests` extended, plus a new test).
11. **What the draft does not claim.** `InPlay` with a defence result is a probability outcome, not a legal fielding record: fielder credits, force / tag categories, every runner's movement, outs order, third out, walk-off, the `reached_on_error` fielder and the `advancement` draw are 3-C2B. The resolver does not check that the supplied batter side and pitcher hand belong to the batter and pitcher currently in the `GameState` (it takes both from the caller); that wiring is 3-C2B / 3-C3.
12. **Verification.** Expected values come from the independent Python oracle (own PCG32 and `kd1`; the baseline rows are read directly from `content/tuning/virtual_tuning_v1.json`; no C# probability or RNG code is shared): 28 scenarios / 55 pitches covering every branch kind (with and without an explicit Take), both call modes, all six defence results, every batter side by pitcher hand combination, non-fresh starting positions, chained pitches and a rejected raw output. 81 new tests; 15 injected defects were all detected (report Part E).

13. **Game / RNG context must match (Codex review, Medium, 2026-10-11).** A random snapshot belongs to one game: `GameState.GameId` must equal `GameRandomSnapshot.ContextKey` exactly (`StringComparison.Ordinal`; no trimming, case folding, id rewriting or default context). The check runs after the snapshot is restored successfully (existing `Rng.*` codes for a missing or malformed snapshot are unchanged) and before the first draw; a mismatch is `PitchBranch.game_context_mismatch`, nothing is drawn, no draft exists and the caller's state and snapshot are untouched. Matching input behaves exactly as before. Test fixtures pass the game id explicitly; the Phase 3-A / 3-C2A golden vectors are unchanged. Accepted with 3-C2A on 2026-10-11 after the Codex focused re-review `PASS WITH NOTES`.

## Decisions (3-C2B-1) — prepared pitch and non-in-play event candidate (Accepted 2026-10-11; 3-C2B-1 only; originally recorded as an unapproved implementation)

Owner instruction `TASK.md`: Codex High returned `CHANGES REQUIRED` for 3-C2B as a whole; GPT Chat approved ONLY the limited 3-C2B-1 implementation. 3-C2B-2/3 and 3-C3 are not started. Code: `src/StarPlayer.Simulation/Baseball/PitchPreparation.cs`; contract text `docs/game-engine.md` section 22; report `docs/reports/PHASE_3C2B1_REPORT.md`. The 3-C2A contracts above are unchanged.

1. **Prepare really calls the resolver.** `PitchPreparation.Prepare` takes the state, the current RNG snapshot, the tuning, the intent, the explicit-Take flag and the two `PlayerSheet`s, calls the unchanged `PitchBranchResolver.Resolve` and keeps its draft inside a `PreparedPitch` (internal constructor, get-only, in-memory only, never saved). No API accepts a caller-made draft.
2. **Players come from trusted sheets.** The sheets' ids must equal `state.Batting.CurrentBatterSlot.Player` and `state.Fielding.Pitcher`; the declared side is `Player.Bats`, the throwing hand `Player.Throws` (switch-hitter policy of 3-C2A item 6). No further eligibility rule; supplying trusted sheets is the caller's responsibility (no player store exists yet).
3. **Coupling.** `BuildNonInPlayCandidate` refuses with a specific code when the game id, the RNG context, the start `StateHash`, the batter/pitcher ids or handedness, the rules version/hash, the tuning version/hash, the probability-model version or the draft contract differ; the `GameState` must also be the very same object (`ReferenceEquals`, checked last). Object identity is a short in-memory life-cycle guard only; it is not Phase 4 integrity and not 3-C3 atomicity. A structurally broken snapshot keeps its `Rng.*` restore error.
4. **Mapping.** Exactly five branches: `HitByPitch`, `CalledBall` (Ball), `CalledStrike`, `SwingingStrike`, `Foul` become a `PitchEvent`, or a `TakeEvent` for an explicit Take (Take + swing/foul = `take_cannot_swing`). `Location` = the draft's location; Mishap/DroppedThirdStrike None, no Moves, `StrikeoutCredits` null; forced advances and strikeouts stay the reducer's. Events with a location are `ef2`.
5. **In play is an explicit limit.** `PitchBranchKind.InPlay` returns `PitchCandidate.in_play_not_supported_yet`: no redraw, no kind change, no event, no id, nothing adopted.
6. **Working id.** The authoritative last sequence is read-only input; a private `GameEventIds` issues `Next()`; the id must not already be in `AppliedEvents`; the caller's cursor is never changed; the receipt count is never used. Finalising the id is 3-C3's job and must not substitute another value.
7. **Reducer check.** The candidate is applied to the original state by the unchanged `GameReducer.Apply`; an error is returned as the failure, `WasDuplicate` is never a new success, the receipt must be `ef2` with the candidate id, and the pitcher's pitch count must rise by exactly one. The resulting state/receipt are an UNCONFIRMED preview (`UnconfirmedStep`) and are published nowhere.
8. **No randomness.** Zero extra RNG calls, nothing on `game/runner@1`; `NextRng` equals the draft's next position (call counts: HBP 3, ball/strike 4, swing/foul 4). The golden chain ends exactly on the oracle's final RNG text and hash for every scenario.
9. **Resolver-internal.** `PreparedPitch` and `NonInPlayPitchCandidate` join the Application/Infrastructure signature guard.

The instruction states that the owner explicitly approved prototype policies D1–D5; it does not give the date of that approval, so this section is dated by the day it was written into the ADR (2026-10-12). **This is a policy approval only.** No 3-C2B-2 code exists: nothing under `src/` changed, the in-play candidate generator is not implemented, and the template verification below was done with test-only tooling (`tests/StarPlayer.Simulation.Tests/InPlayFeasibility/` and an independent Python oracle). 1. **Approval date and scope.** D1–D5 below are approved as **prototype** policy for the in-play stage of the pitch resolver (3-C2B-2 and the 3-C2B-3 / 3-C3 steps that consume it). They do not approve any implementation, any later phase, KBO certification of a rule, or a calibrated statistic.
2. **D1 – meaning of a drawn long hit.** `inplay-mapping-v1` is introduced. A 3-C2A `defense_result` of `double` or `triple` is interpreted at mapping time as a *potential* base hit. In ordinary game situations the drawn result is kept as the official result. In the last half of the final or an extra inning the official bases are decided from predefined play facts (`walkoff-credit-v1`, item 3). The original draw is never modified or re-drawn; the existing `pitch-branch-v1` output format and its golden vectors are unchanged. This widening of what a drawn `double`/`triple` means is an **approved interpretation owned by `inplay-mapping-v1`**, not a change to the 3-C2A contract.
3. **Versions.** `inplay-mapping-v1` (generation policy: template selection and runner movement), `walkoff-credit-v1` (official record of a game-ending hit) and `inplay-template-v1` (the 19-template catalogue). The walk-off rule: with `need` runs required to take the lead and the runners that would score on the drawn hit ordered lead runner first, the *winning-run scorer* is the `need`-th of them; the official bases are `min(drawn bases, bases that runner advanced)` (OBR 9.06(f)); the facts of the play are those of the template of the official result (the batter really stops where the record says, item 6). A drawn single, a ground out or a reached-on-error is never reduced; a home run is item 7.
4. **Relation to the 3-C2A meaning.** 3-C2A drew `defense_result`; nothing was said about bases or runners. 3-C2B-2 now says what each drawn result means as a virtual play. The draw, its stream positions and its audit step stay as recorded; only the mapping to facts is new.
5. **Responsibility split.** (a) *Virtual play fact generation* (template, fielder credits or error, runner movement, batter destination) is deterministic and consumes no random number. (b) *Official record determination* (the official `InPlayResult`, the credit in a walk-off, and the hit/RBI/error classification by the unchanged `GameReducer`) comes after the facts. The official record is never used to rewrite facts after the draw, and facts are never invented to make a record fit.
6. **D3 – batter destination.** In v1 only virtual plays in which the batter-runner's actual final base equals the officially credited base are generated. This is a generation limit, **not** a claim that the two facts are always equal in baseball. A play in which the batter touched third but only a double is credited (OBR 9.06 comments) is outside the v1 generation range. No false reached-base value is put into a reducer input (the reducer refuses it: `Game.batter_move_invalid`), and no fact is edited after the draw to match a record.
7. **D2 – home run.** A drawn `home_run` means an out-of-the-park home run. Inside-the-park home runs are not generated by this policy. A game-ending out-of-the-park home run scores the batter and every runner (OBR 9.06(g), 7.01(e)(3) exception); the result is never changed to a single or a double.
8. **D4 – rule basis; KBO not certified.** The confirmed 2026 OBR (`docs/2026-official-baseball-rules.pdf`, original text read 2026-10-12) is the **temporary prototype basis**: 9.06(a) and (f) with the (f) Comment, 9.06(g), 7.01(e)(3) and its exception, and the Infield Fly definition with its comment. The corresponding **2026 KBO clauses were not found or certified**. The prototype simplifications are approved as prototype behaviour and must never be described as KBO certification (consistent with project invariant D2 and the evidence file `content/rules/game_rules_evidence.json`).
9. **D5 – audit and replay contract (design only, Simulation-internal).** One evidence record per in-play candidate with: inplay policy version, walk-off credit version, template catalogue version; the original batted-ball class and intensity; the original `defense_result`; the final official `InPlayResult`; the selected template id (and the drawn template id when different); the situation before the play (outs, runners with their keys, score, inning, half); the batter's final base; every runner move (runner key, from, to, cause) in scoring order; the winning-run scorer; the reason the official record differs from the drawn result; `GameId` and the final candidate `EventId`; rules profile id/version/hash, tuning version/hash and probability model version; the start and the final RNG `StateHash`. It is **not** part of the `ef1`/`ef2` canonical text and does not change event JSON, receipts, golden vectors or any hash. 3-C3 must settle the evidence, the `GameEvent`, the receipt, the state, the RNG and the ids **together**; Phase 4 stores them durably. Neither is implemented here and no database work was done.
10. **Responsibility boundary.** *3-C2B-2:* template selection, base runner movement, the walk-off official record, an explicit advancement-required flag, `BaseInPlayPlan`, a reducer-validated `InPlayPitchCandidate` for complete plans and a `PendingAdvancement` for the rest; **no RNG after the draft** (zero extra calls). *3-C2B-3:* the `advancement` draw on `game/runner@1` for a `PendingAdvancement`, the resulting runner changes (including a runner out on the bases and its credits), a fresh walk-off record and third-out ordering. *3-C3:* joint atomicity and automatic plate-appearance progression. *Phase 4:* durable storage and the expected RNG hash.
11. **Unresolved technical matters (not decided here).** (U-1) `prob-model-v1` declares four `advancement` contexts (single with a runner on first, single with a runner on second, double with a runner on first, fly out with a runner on third) and nothing for situations with more than one runner; 210 of the 300 pending ordinary cases and 654 of the 1,014 pending walk-off cases are such composite situations, so 3-C2B-3 must define the context, the order and the interaction before it draws. (U-2) After an `advance_extra` or `out_on_bases` result the walk-off record and the third-out order must be recomputed (3-C2B-3). (U-3) The templates fix the fielder of every out and error; this biases defensive statistics and produces no double play, fielder's choice or sacrifice; calibration is 3-F. (U-4) KBO certification of the rules used (item 8). (U-5) The Infield Fly rule is not modelled by the reducer; it is kept apart only by an explicit template premise (a pop-up caught by an infielder vs. one beyond the infielders' ordinary effort). (U-6) On a play that makes the third out the base plan holds every runner (no run, so no out/run order is needed); this is conservative, not a baseball claim. (U-7) The last issued event sequence must be re-checked in 3-C3 (carried over from 3-C2B-1).

3. **D-3 Single confirmation gate.** Non-in-play pitch events, base in-play events, in-play events with a resolved extra-base decision, `ApproachEvent`, `RunnerPlayEvent` and `SubstitutionEvent` pass one common Stage/Publish boundary. Creating an event and confirming it are separate responsibilities. An event that consumes no random number preserves the existing RNG. C3 builds no event generators and no PA driver.
4. **D-4 PA driver separated.** C3 owns only the safe confirmation of a candidate or proposed event. The next-action choice, new candidate generation and the whole PA loop belong to the later 3-F harness. Any difference from ROADMAP is recorded, not resolved by editing it (`docs/game-engine.md` 27.14).
5. **D-5 Finalize atomicity.** When an official game-ending event is confirmed, `GameReducer.Finalize` runs in the same Stage; a `Finalize` failure means no Publish; a final game with `Final == null` is never published as an official state; `Finalize` issues no extra EventId or receipt and consumes no RNG; the completed final state is one atomic Publish.
6. **D-6 Re-submission.** A candidate that was already confirmed is never accepted again; the result is `already_committed` or a rejection that fits the existing freshness contract. The exact error priority is fixed in the C3 implementation contract, the existing `CheckPrepared` codes and order are not changed arbitrarily; a duplicate confirmation must not advance RNG, EventId or game state.
7. **D-7 Adopt the re-run reducer result.** Stage re-runs `GameReducer.Apply` on the CURRENT authoritative `GameState` and the re-run result is the basis of what is adopted. The candidate's `UnconfirmedStep.State` is a verification preview and is not adopted unconditionally. The two are compared structurally, at least: the event receipt and event history; runs, outs, runner placement and ball/strike count; inning and game-end state; `ScoredPlay` and its `Sequence`; RBI, at-bat, left on base and the official records; `Delta` and `Facts`; and the other nested game state an event changes. `GameState ==` is not used as proof of full structural equality. A difference rejects the Publish. For a game-ending event, `Finalize` runs after the re-run result and the preview have been checked.
8. **D-8 Inside Simulation.** The authoritative aggregate and the gate live inside the Simulation layer; hidden candidate/prepared/audit types do not appear in any public Application/Infrastructure signature (`HiddenTendencyBoundaryTests` stays satisfied). No new repository, database persistence or UI API in C3.

**Additional approved contracts.**
- **A `AuthoritativeGame`:** immutable reference type; conceptual fields `GameState`, `GameRandomSnapshot`, `LastEventSequence`, `Revision`, `LastCommit`; `Revision` is a monotonic `long` that increases on every successful Publish; `AppliedEvents.Count` is an auxiliary consistency check only.
- **B Stage/Publish and CAS:** Stage takes the current aggregate and computes the new state and a `CommitRecord`; a failure leaves the authority unchanged; Publish compares the expected aggregate reference with the current one by CAS; of two or more changes prepared from the same base exactly one succeeds; cancellation is handled only before the final CAS and a CAS success is never reported as cancelled. `Revision` and CAS are different things (identity check in memory vs. a monotonic value that storage can compare).
- **C RNG verification:** `NextRng` snapshot validity; master seed equal; context key equal; streams present at H0 preserved; per-stream `Draws` never backwards; the candidate draft's raw-draw increase equal; the advancement context's raw-draw increase equal; new and existing streams consistent with the recorded usage. A hash match is never recorded as proof of the generation path; the trust boundary of the internal candidate generators and the remaining limit are documented (`docs/game-engine.md` 27.8).
- **D Candidate source link:** the non-in-play adapter uses the internal pair `(PreparedPitch, NonInPlayPitchCandidate)` to minimise changes to existing types; a wrongly linked pair is never treated as valid, and the verifiable matching conditions among the original state, the event, the pitch information and the RNG usage record are defined (`docs/game-engine.md` 27.9). An in-play candidate reuses `Plan.Prepared`. A `PendingAdvancement` is not a confirmable candidate.
- **E `CommitRecord`:** immutable data with only what verification and later storage need (confirmed event, receipt, RNG hashes, event sequence, revision and the like); no hidden candidate type leaks; in-memory audit sources and the persistence data Phase 4 needs are kept apart.
- **F Persistence:** C3 guarantees atomic in-process publication of state only. SQLite transactions, recovery from a failed save and the order "persist, then publish to memory" are Phase 4 hand-off contracts; a CAS alone is not recorded as solving persistence atomicity between a database and memory.

**Authorised split (design only; each part's code is a separate authorization).** C3-A gate foundation (aggregate, `Revision` and CAS, `StagedCommit`/`CommitRecord`, canonical ids and continuity, official events without RNG, `Finalize` in the same Publish, basic duplicate/freshness checks); C3-B pitch-candidate integration (non-in-play pair adapter, in-play adapter, `CheckPrepared`, H0/H1/H2 and per-stream raw draws, reducer re-run, structural preview verification, `ef2` receipt and pitch count); C3-C stability and regression (same-candidate re-submission, concurrent confirmation of different candidates, CAS races, stale candidates, failure/cancellation invariance, deterministic retry, game-event replay equivalence, `Finalize` atomicity, C2B-1/2/3 regression, full xUnit and the project gate, the implementation report and an independent review).
