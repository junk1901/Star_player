# ADR-002 — Hidden-data exclusion by construction and the Phase 1 observation placeholder

- Status: Proposed — Phase 1 implementation decision, awaiting GPT Chat / owner review (`검토 대기`). Amended 2026-10-10 after the independent Codex review (`CHANGES REQUIRED`, 4 findings); amendments are items 8–11 and the revised items 2 and 5.
- Date: 2026-10-10
- Scope: Phase 1 only. No product rule changed; all items are implementation choices inside AGENTS.md invariants.

## Decisions

1. **Exclusion is structural, not a filter.** `DevelopmentProfile` (true potential, growth type, prime, decline onset, per-skill ceilings) is not a member of `PlayerSheet`; the visibility policy takes a `PlayerSheet`, so it can never receive hidden data. Public DTOs (`PlayerPublicView` …) reference no Domain type. `HiddenDataGuard` is only a last-line text scan, and tests prove that rewriting every hidden value leaves every projection byte-identical.
2. **Authority is the trusted binding, not the request or the options.** `PlayerQuery` carries only a player id. `ViewerContext` is internal with no public constructor. *Revised:* `PlayerSessionOptions` no longer has a player id (only `CheatMode`); "my player" comes from the world's own binding (`controlled_player_id` in the pack, the Phase 1 stand-in for the Phase 4 career binding). The original design let any caller of the public `PlayerInfoService` constructor pass an arbitrary `ControlledPlayerId` and so impersonate an NPC (Codex High). A hostile payload with `IsSelf`/`CheatMode`/id fields is ignored by deserialization.
3. **Cheat mode widens nothing in Phase 1.** Cheat means free creation ratings within 0–100 (source v1.6); it does not reveal NPC current values, potential or growth type. If the owner wants cheat to show exact NPC current ratings, that is a product decision to add later, never potential.
4. **`observation-v0` is a placeholder** until Phase 12 scouting: a pure function (no RNG, no clock) that returns the fixed-width bucket containing the real value (width 10; 5 for club-mates), never a zero-width range, grade letter from the bucket midpoint. It cannot be wrong, which Phase 12 will change.
5. **Fixture pack is embedded in `StarPlayer.Infrastructure`.** The export has no loose content folder, so `content/fictional/phase1_two_club_pack.json` is an `EmbeddedResource`. It is a Phase 1 test fixture source behind the *internal* Application port `IPlayerWorldSource`, not the Phase 4 datapack importer.
6. **Domain stays serialization-free.** JSON schema v1 lives in Infrastructure DTOs; every value passes through Domain factories on read, and the writer is the exact inverse (`write(read(pack)) == pack`).
7. **`ClubId` is added beside `TeamId`.** C47/C06 speak of ClubId (franchise); Phase 0's `TeamId` is kept for competition squads and is unused by Phase 1 data. A later phase may unify them under an owner-reviewed rule.

## Amendments after the Codex review (2026-10-10)

8. **The raw world is unreachable from the client by construction.** `PlayerWorld`, `IPlayerWorldSource`, `ViewerContext` and the `PlayerInfoService` constructor are `internal` in Application; `FixturePlayerWorldSource`, `WorldJson` and the DTOs are `internal` in Infrastructure. `InternalsVisibleTo` is limited to Infrastructure and the test assemblies (the client is not listed) and pinned by a test. The client's public Infrastructure entry points are `PlayerInfoComposition.CreateFictionalPhase1(PlayerSessionOptions)` and `SqliteStorageDiagnostics`. No new layer or assembly was added.
9. **Bootstrap and presenters share one assembly, so a namespace rule is not the guarantee.** The guarantee is visibility (item 8). Defense in depth: reflection over the public surface of Application and Infrastructure (no Domain type, no raw world, no hidden profile, ports, factories, constructors, parameters named like a controlled player), a compiled-IL scan of the client (only `CompositionRoot` touches Infrastructure; nothing touches Domain/Simulation), and a source scan for raw-world type names. The detectors were mutation-checked.
10. **C47 across clubs.** A player may hold at most one number at any time regardless of club; `ActiveOn` returns a `Result` and reports `conflicting_active_rows` instead of picking a row. Intervals stay half-open `[from, to)`.
11. **C40 snapshot immutability.** `RuleAreaDefinition`/`RuleSimplification` are immutable classes built through validating factories; inputs are defensively copied; public collections are read-only copies; `default(RuleVersionId)` is invalid; versions of one area may not overlap. Simplifications became `{id, description}` objects (pack schema v1 changed accordingly, before any commit).

## Consequences

- Phase 7 (development) must load `DevelopmentProfile` through its own port; no code path should ever add it to `PlayerSheet`.
- The 850–1150 ‰ park-factor bounds, the 0–99 jersey range and the personality-trait list in the fixture are fixture/vocabulary values, not approved tuning.
- `verify.ps1` now records `PHASE_1_VERIFY_LOG.md`; the approved Phase 0 logs are untouched.
