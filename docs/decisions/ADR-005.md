# ADR-005 — Pitch Zone Lite data contracts: zone model, boundary table, tendency vector, called-pitch mode (Phase 3-B1)

- Status: Accepted — work package 3-B1 was approved `PASS WITH NOTES` by GPT Chat on 2026-10-11 and the Codex focused re-review returned `PASS WITH NOTES`. Amended once after the first independent Codex review (`CHANGES REQUIRED`): item 9, which supersedes the "reference" half of item 5. The approval covers 3-B1 only; Phase 3-B as a whole is not complete and no Phase 3 Gate is claimed. (This status line was brought up to date in Phase 3-B2; no decision below was changed.)
- Date: 2026-10-11
- Scope: data models and one rule-profile extension only (`src/StarPlayer.Domain/Baseball/PitchZone/`, `GameRules.cs`, the GameRules JSON reader, `content/rules/game_rules_profiles_v2.json`). Implements ROADMAP §1.14 and the 3-B "model and tuning contracts" part that concerns zones, boundary class, tendency and call mode. No pitch location is drawn, no event / `ef1` / `ef2` / reducer / RNG code changed, and no probability, resolver, calibration or persistence exists.

## Decisions

1. **One `ZoneModelVersion` owns zones, boundary table and catcher's-view convention.** `pzl-zones-v1`. A change to any of them is a new version. A separate version axis for the boundary table was rejected: it would let a stored (zone, class) pair be read under two different meanings.
2. **The boundary class is a deterministic function of the zone** (ROADMAP: "assigned from a versioned table keyed by zone"). Rule: a region sharing an *edge* with the strike-zone outline is `Borderline` (the 8 non-centre inner cells and `out.high`, `out.in`, `out.low`, `out.out`); the centre cell and the four diagonal outer zones are `Clear`. Alternative considered: allow `Clear` or `Borderline` per zone and draw the class. Rejected for 3-B1: it adds a second random draw and consumption-order decision to `game/location` that nothing yet needs, and the deterministic table is what the roadmap states. Consequence: framing in 3-E acts on 12 of the 17 zones, so its cap, not the class, must carry the magnitude. If 3-B2/3-E calibration shows this is too coarse, a new `ZoneModelVersion` with a finer table is the route. The choice is a virtual game-model decision, not a measurement of any real strike zone, and claims no ABS accuracy.
3. **Illegal combinations are rejected at construction.** `PitchLocation.Create` refuses a class that is not the table's class; unknown versions, unknown zone text, undefined enum values and `default` ids are errors. `PitchLocation` and `TargetZone` are separate types; a target has no side or class.
4. **Applied side is a pitch fact, declared side is a player fact.** `AppliedBatterSide` {Right, Left}; `BattingSide.Switch` can never be a location's side. Validation only checks possibility; the switch hitter's per-pitch choice rule is deferred to 3-C. Catcher's-view convention: a right-handed batter's inside is the catcher's left (a model convention, versioned with the model).
5. **Tendency vector: integers, `-100..+100`, resolver-only, average-neutral.** Integers avoid a floating-point contract. The value is a fraction of a per-zone cap that 3-B2 defines, so the data contract does not pre-empt tuning. Neutrality is exact: the sum of `value x reference weight` is 0 against a named `ZoneReferenceDistribution`; `UniformV1` is an *interim* reference and is not a claim about real pitch locations (3-B2 may add a tuned reference under a new id). Exact integer neutrality is stricter than a tolerance; if a tuned non-uniform reference makes it too awkward to author vectors, 3-B2 may add a normalising constructor, not loosen the check. Hidden: no accessor outside the resolver is planned; `ToString()` redacts; a reflection test pins that Application and Infrastructure carry the type in no member signature.
6. **`CalledPitchMode` is part of C40's `GameRuleSnapshot` as an optional pair with the zone model.** `null` means "this profile does not say" and stays distinct from both modes; `FramingMayChangeCalls()` errors for it instead of guessing. Alternative rejected: defaulting legacy profiles to `NonAutomated` (would assert a rule the profile never stated) or to `Automated` (would silently claim the real 2026 ABS).
7. **Legacy hash preserved by construction, not by luck.** The v1 canonical text is untouched and the v2 suffix is appended only when a mode is declared. Seven legacy hashes are pinned in a test against values computed by an independent Python script before any code change. New fields in an old-format file are rejected as unknown members, so a legacy profile cannot gain a field silently; v2 profiles live in a separate `format_version` 2 file with their own (fictional) ids.
8. **No consumer wiring.** `ScriptedGameSource` still loads only the legacy pack; the v2 file is embedded and tested but used by no game yet (3-C).
9. **A reference id and its weights are one immutable definition (fix round, Codex High).** The first version let `ZoneReferenceDistribution.Create` build any id with any weights, so the stored `ReferenceId` `pzl-ref-uniform-v1` could have judged a tendency under `[3,1,1,1,1,1,1,1,1]` and passed a vector (`[1,-3,0,...]`, really -2 against nine ones) that the real UniformV1 rejects. Now: only registered definitions exist; `UniformV1` (`pzl-ref-uniform-v1`) is **exactly** `[1,1,1,1,1,1,1,1,1]`; `Resolve(id)` returns the registered one or `ZoneReferenceDistribution.id_unknown`; `Create(id, weights)` is a confirmation for reading stored data - unknown id -> `id_unknown`, known id with other weights -> `weights_mismatch`, otherwise the registered instance; there is no public constructor or other public way to build an unregistered reference (an `internal` factory exists for `Domain.Tests` only, the sole `InternalsVisibleTo`, to exercise the weighted-sum logic). A bad input is never replaced by a neutral default and no id was renamed to hide the problem. Immutability: private constructor, weights copied into an immutable array on creation (a caller's array cannot change it), no public setters. The weighted sum is a `long` over range-checked values (|v| <= 100) and weights (<= 1,000,000): at most 9e8, no overflow path. **Rule for any future reference** (for example a tuned one in 3-B2): add it to the registry in `BatterZoneTendency.cs` under a NEW version id with its fixed weights; never change the weights of an existing id and never pass other weights under an old id. A stored tendency's `ReferenceId` therefore always resolves to the weights that judged it. Alternatives rejected: keeping the open factory and comparing ids on use (the invalid object would already exist), and storing the weights inside every tendency (duplicates the definition and lets two tendencies with one id disagree).

## Consequences and open points

- 3-B2 must fix, before any calibration run: the integer probability scale, the per-zone tendency cap, the tuned (or confirmed uniform) reference distribution, and the baseline conditional probabilities by zone / class.
- 3-C decides the number and order of `game/location` draws per pitch (a zone draw; the class needs none) and the switch hitter's side rule, and adds the `PitchEvent`/`TakeEvent`/`InPlayEvent` location payload and `ef2`.
- 3-E decides the Framing cap and the computation; the contract fixed here is only "Automated -> exactly 0; NonAutomated -> Borderline only, within a cap, never changing a committed call".
- Not in this ADR and not decided: which `CalledPitchMode` the production KBO-oriented profile should declare. The legacy `kbo-oriented-unverified-v0` stays undeclared; a production v2 KBO profile needs evidence and an owner decision (existing evidence row R24 only confirms ABS exists).
