Implements the "model and tuning contracts" part of ROADMAP Phase 3-B and §1.14 / §4.1. **No pitch is resolved, no random number is drawn, no event, `ef1`/`ef2`, `GameReducer`, rule profile or RNG stream changed, nothing is persisted, and no statistical calibration was run.** All numbers are a **virtual prototype**, not statistics of KBO, MLB or any real league.

## Decisions

1. **Scale: parts per million, denominator `1,000,000`.** A probability is a whole number of ppm in `0..1,000,000`; every conditional distribution sums to exactly `1,000,000`. Checked against the existing integer scales: skills 0–100, tendency −100..+100, C46 permille 1000 and money in KRW all divide it, so no conversion loses precision; one ppm is fine enough that a 0.1% modifier on a 1% outcome (10 ppm) is still a whole number of units; and it fits the `uint` bound of `RngStream.NextBounded` (ADR-004 item 2). Rejected: 10,000 (basis points) — a 1% outcome would have only 100 units, so a −5% modifier would round visibly; 2^32 — not a power the stage tables can be read in. The code never uses `double`, `float`, `decimal` or `Math.*` on probabilities; a source-scan test pins this.
2. **Normalization rule `largest-remainder-lowest-index-v1`.** Non-negative integer weights → exact total: each outcome gets `floor(w·T/S)`; the leftover units (fewer than the number of outcomes with a non-zero remainder) go one each to the largest remainder `(w·T) mod S`, ties to the **lowest index**. A zero weight is exactly zero and never receives a unit. Arithmetic is `Int128`; accepted range 1–64 outcomes, weight `0..2^56`, total `1..1,000,000` — anything else is an explicit error (`Probability.*`). Property: output is a pure function of the ordered weights; scaling all weights by a constant gives the same result. Limit recorded by a test: a negligible positive weight can still round to zero (`[2^56, 1] → [1,000,000, 0]`), which is why decision 7 requires a floor on positive baselines and why the stage computation re-checks that no baseline-positive outcome was lost.
3. **Product rounding `half-up-v1`.** `round(v·n/d)` on non-negative operands, half up, `Int128` intermediate, range-checked to `long`.
4. **Roll contract (no RNG consumed here).** One categorical decision = **one** `RngStream.NextBounded(1,000,000)` call = one roll; `Distribution.Select(roll)` maps it to the outcome whose cumulative ppm interval contains it (outcome `i` owns exactly `Ppm[i]` consecutive rolls, a zero-ppm outcome is never selected; `roll ≥ 1,000,000` is an error). Verified exhaustively over all 1,000,000 rolls. **Handoff fact for 3-C:** `NextBounded` rejects raw outputs below `(2^32 − 10^6) mod 10^6 = 967,296`, so about 0.0225% of raw outputs are skipped; a decision is one call but can advance the stream's `Draws` by more than one. 3-C must count decisions by calls and keep `Draws` as the audit value, never assume `Draws == decisions`.
5. **Conditional structure `prob-model-v1` (ROADMAP §4.1 order).** Each stage is a family of distributions over its own mutually exclusive outcome set, conditioned on a named outcome of an earlier stage. A stage's denominator is "given that condition" and is never mixed with another stage's totals; a joint path probability is the product of its stage probabilities (a test sums every path through the batter-response stages with `BigInteger` and gets exactly `D⁴`).

6. **Tuning profile = versioned data with a deterministic identity.** `TuningProfile` carries: model version `prob-model-v1`, tuning version `tuning-virtual-proto-v1` (only versions this build knows can be created), status `virtual_prototype`, provenance text, zone model `pzl-zones-v1`, reference distribution `pzl-ref-uniform-v1` (resolved through the ADR-005 registry), normalization/rounding policy ids, the 105 baseline rows, the modifier tuning, the combined cap, the tendency caps, the declared validation scenarios and the declared calibration targets. **Identity** is `ContentHash` = SHA-256 of a canonical text built from the *validated* values in a fixed order (model stage/condition order, slot order, scenarios/targets sorted by id); JSON key order, whitespace, list order and the free-text descriptions do not change it, every number, id and the provenance do. The hash `5b70dca7…3ea5` is pinned by a test and was computed first by an independent Python implementation (`tests/Fixtures/generator/gen_virtual_tuning_v1.py --hash`) whose result the C# value matched on the first run. A changed number is a new hash and, by policy, a new `TuningVersion`; the JSON reader builds only an unvalidated draft and `TuningProfile.Create` makes every validity decision (so each rule has a mutation test that must be rejected).
7. **Baselines are virtual prototype values; selection rationale and review targets.** They are design choices for a fictional league, chosen so the model behaves plausibly (a pitcher mostly hits the aimed zone, hard contact is likelier in the heart than at the edges, a hard fly ball is the likeliest home run) and so every structural rule can be exercised. They are **not** derived from any real data and **no accuracy is claimed**. Derivation (reproducible, documented in the generator): target zone from per-intent weights; actual location = 50% on target for an inner target (40% for an outer one) plus the rest spread over the other zones by Chebyshev distance 1/2/3 with weights 8/3/1 on a 5×5 layout of the 17 zones; swing, called-strike, whiff, batted-ball and defence rows hand-set per zone class. **For the reviewer to judge:** the swing/call/whiff rows, the 10 batted-ball and defence rows and the four advancement rows are the least defensible numbers; 3-F replaces them under pre-declared targets. *Disclosure:* before the profile was frozen (and before any sampled run) an exact-arithmetic check of the first draft showed an in-zone pitch share of 0.738 against the intended 0.45–0.65, so the target-zone weights were moved toward the outer zones twice until the balanced share was 0.640; that is table design, not calibration, and the final tables are what the pinned hash covers. For the record, exact arithmetic on the frozen tables with neutral inputs gives, per intent (`balanced`/`attack`/`careful`): in-zone share 0.640/0.703/0.605, swing share 0.508/0.537/0.487, whiff per swing 0.230/0.222/0.237.
   Validation at creation also enforces: every row complete and in model order; a positive baseline is at least `MinPositiveBaselinePpm` = 1000 (an impossible outcome is an explicit `0`); a hit-by-pitch only on an outer zone on the batter's inside and at most 10%; `automated` calls are a hard line (inner = strike, outer = ball); `non_automated` calls are near-certain (≥95%) on `Clear` zones and genuinely uncertain (each side ≥5%, leaning toward the zone's side of the line) on `Borderline` zones.
8. **Modifiers: fixed order, per-slot caps, one combined cap, no double counting.** A slot (model data) names its stage, its target outcomes, its input kind and its documented monotone direction; the tuning supplies numbers.
   - *Linear* slot: `factor = 1,000,000 + (input − neutral) × slope`; the sign of the slope is fixed by the model (`pitcher.stuff` up, `batter.contact` down, …) and the factor at both ends of the input range must lie inside the slot's own `[min, max]`. *Table* slot (`strategy.approach`, `situation.count_pressure`, `matchup.handedness`): named choices whose factors may not decrease along the model's order, with `neutral` exactly `1,000,000`.
   - Per outcome the factors of the slots that target it multiply **in the model's slot order** (pitcher, battery/catcher, batter, strategy, situation, matchup, defence, park, runner within each stage) with half-up rounding, then are clipped to the **combined cap** `[800,000, 1,250,000]`; weights are `baseline × combined factor` and are normalized by decision 2. The profile requires `combinedMin × 2 ≥ combinedMax`, so the worst-case relative change of a positive baseline is ≥ 0.64 and it cannot vanish; a final invariant check still fails loudly if a baseline-positive outcome reaches 0.
   - Slot caps (live): Stuff ±6%, Control/Eye/Contact/Power ±7.5%, Speed/Arm ±10% per slot at the ends of 0–100 (neutral 50); Velocity ±4%; Fielding ±4%; approach 0.88–1.10; count pressure 0.88–1.10; handedness 0.97–1.04. All slot ranges lie inside the combined cap.
   - **Neutral is exact.** A neutral input is a factor of exactly `1,000,000`; `1,000,000 × baseline` normalizes to the baseline unchanged (test over all 105 rows, with every slot supplied at its neutral).
   - **No double counting, by construction.** Each ability input feeds exactly one slot; the same slot twice is `Modifier.duplicate_input`. Power acts only on hard-contact share in `batted_ball` (the home-run chance is already conditioned on the batted ball, so Power is not applied again there). `defense.fielding` is ONE effective value the caller derives once from rating and position proficiency. The three park slots own disjoint outcomes (`home_run` / `single` / `double`+`triple`). Eye acts only on outer zones (`ZoneScope.Outer`), recorded in the trace as not applied inside the zone.
   - **Player ratings cannot change:** the model takes plain integers; a reflection test pins that no type in the probability namespace names anything from `StarPlayer.Domain.Players`.
   - **Reserved slots (future contracts, neutral input only):** `catcher.framing` (3-E; must stay exactly zero in `automated` mode and act only on `Borderline` in `non_automated`), `catcher.game_calling`, `battery.chemistry` (Phase 7; pair-specific effective performance only), `park.home_runs`, `park.hits`, `park.extra_base_hits` (3-D; a C46 permille 1–3000, 1000 neutral). Their tuning has **no numeric authority** (slope 0, min = max = `1,000,000`; the profile rejects anything else), a non-neutral input is `Modifier.reserved_not_active`, and the later package that owns the effect adds its caps under a new tuning version.
9. **Pitch Zone Lite tendency.** Not a modifier slot: it is a mass shift on two stages, after normalization. `swing_result` (favourable = `foul` + `in_play`, cap `60,000` ppm) and `batted_ball` (favourable = `ground_hard` + `line_hard` + `fly_hard`, cap `40,000` ppm). The shift is `value × cap / 100` ppm (caps are multiples of 100, so it is exact; `+100` = the full cap in the batter's favour), taken from or given to the other outcomes in proportion to their probabilities, with **both sides keeping exact totals** (`Normalize` per side). Outer zones get no shift; the stored `ReferenceId` must equal the profile's reference.
   - **Window guard.** When a `TendencyContext` is supplied, the favourable mass is first clamped to `[cap + minMass, D − cap − minMass]` (`minMass` = 1000), a clamp that does not depend on the vector, then shifted. The shift is therefore never clipped, both sides stay positive, and "no tendency" and an all-zero vector are the same computation. The baseline of every inner zone is validated to lie inside the window (a tuning that violates it is rejected), so the guard binds only when ability modifiers push a zone to the edge (exercised in a test with a deliberately wide cap).
   - **What neutrality means here, exactly.** Against `pzl-ref-uniform-v1`, for any vector accepted by `BatterZoneTendency.Create`, the sum over the nine inner zones of the favourable mass **with** the vector equals the sum **without** it, as an exact integer equality (stage-level, and also with extreme ability inputs). **What is not claimed:** that the batter's league-average output is unchanged. The real pitch mix is not uniform, so weighting the same shifts by the actual zone mix and by the chance of reaching the stage gives a generally non-zero average; a test documents that gap for the shipped mix, bounded by the cap. Because of that, the reference stays `pzl-ref-uniform-v1` (unchanged, weights `[1×9]`); a mix-weighted reference would need a new registered id and re-authored vectors and is a 3-F decision after real mix data from the resolver exists.
10. **Pitch Zone Lite probability contract.** `pzl-zones-v1` zone definitions and boundary table are untouched (5 `Clear`, 12 `Borderline`). The zone→class split matters in `called_pitch` (per zone and per mode), the 17-zone order is the single canonical order used by stages 1–3 and 5, `pitcher.control` (reserved neighbours: `catcher.game_calling`, `battery.chemistry`) raises the on-target outcome (`@condition`) of `actual_location`, and the actual location is the distribution of stage 2 conditioned on the target — drawn **before** any outcome stage. `GameReducer` stays the sole authority over official counts and calls.
11. **Trace.** `ProbabilityTrace` records model/tuning version and hash, zone model, reference id, normalization policy, stage and condition, outcome ids, the baseline, every supplied modifier (slot, input, factor, targets, applied or not), the per-outcome combined factor and whether the combined cap clipped it, the distribution after modifiers, the window-guard shift, the tendency shift (signed ppm of favourable mass) and the final distribution. A test re-derives the result from the recorded facts alone. It is resolver-internal: the tendency shift of one zone is derived from the hidden vector, so `TendencyContext`, `ProbabilityTrace` and `StageResult` are added to the signature guard that fails the build if any Application or Infrastructure member names them; `ToString()` prints no value. No display API exists.
12. **Pre-declared scenarios and targets (fixed before any run).** Four distribution-level scenarios (profile data, hashed): the draw of `actual_location` given `in.r2c2`, `batter_decision` given `in.r1c1`, `called_pitch` given `non_automated:in.r1c2` and `defense_result` given `fly_hard`, each with its own fixed seed (`2026101101`–`2026101104`), context key, 200,000 samples and the rule `binomial-4.5-sigma-ceiling-v1` (`|observed − expected| ≤ ceil(4.5·√(N·p·(1−p)))`, exact for `p ∈ {0, 1}`). They were declared in the data before the first run and **passed on the first run**; seeds and tolerance were not adjusted. They exercise the distribution↔`NextBounded` link on a throw-away generator with a test-only stream name — never a `game/*` stream. Eight aggregate targets (strikeout, walk, hit-by-pitch and home-run rate per PA, BABIP, in-zone share, swing share, whiff per swing) are **declared** with their allowed ranges and status `declared_for_3f_not_evaluated`; 3-B2 evaluates none of them, runs no 100,000-PA or 100-game calibration, and does not claim Phase 3-F.

## Amendments after the Codex review (2026-10-11): items 13-15

No earlier decision, number, tuning value or hash changed; the fix round touched storage and input checking only.

13. **Deep immutability of the public object graph (Codex High x2).**
    - *Causes.* (a) `Distribution` stored `string[]`/`int[]` and returned them as `IReadOnlyList`: the interface type hides the writer, a cast does not, so `(int[])d.Ppm` could change the public table while the private cumulative table that `Select` reads kept the creation-time values (Codex: `[400000, 600000]` → public sum 600000, `Select(0)` still the first outcome). (b) `ProbabilityModel.V1` was built from arrays and `List`s (`params string[]`, `ToArray()` condition arrays) and published them through `IReadOnlyList` members of a **shared static** instance, so one consumer's write changed the model for all (reproduced: after one write the next ordinary profile load failed with `Tuning.baseline_outcomes_mismatch … tampered`). (c) `TuningProfile.Modifier(...).Table` was a writable `List<KeyValuePair<…>>`; changing a factor changed every later calculation (swing 320388 → 348837 ppm on `out.low`; Codex: 568966 → 600000) while `ContentHash`, computed once at construction, stayed the same — the hash no longer described the values in use.
    - *Fix.* Every collection that a public member of `Distribution`, `ProbabilityModel` (stages, conditions, outcome ids, slots, targets, table orders, tendency stages), `TuningProfile` (modifier tables, scenarios, targets, reference weights) and `ProbabilityTrace` / `TraceModifier` can return is an `ImmutableArray<T>` created by copying at construction (`Distribution.Create`; the model and profile constructors re-create every nested list with `ToImmutableArray()`, so no construction path can leak a builder list). A boxed `ImmutableArray` is neither an array nor a `List` and has no writer (`IList.IsReadOnly` is true, mutators throw). The cumulative table of `Distribution` is built from the same values at the same moment, so the public table and the selection cannot disagree. `ContentHash` and `CanonicalText` are computed from values that can no longer change, so the hash always corresponds to the content in use.
    - *Why immutable storage and not copy-on-read.* Copy-on-read allocates on every `Baseline` / `Modifier` / `Outcomes` call in the resolver's hot path and makes the safety of a shared static model depend on every accessor remembering to copy. Immutable storage is one rule in one place with no per-call cost. Public property types stay `IReadOnlyList<T>` (no API change for callers).
    - *Verification.* A reflection audit (`ImmutabilityAudit`) walks every public property and enumerable element of `Distribution`, `ProbabilityModel.V1`, `TuningProfile` (including each `Baseline` / `Modifier`) and `StageResult` and fails on any array or writable `IList` / `ICollection` / `IDictionary`; tests also try to write through array, `IList` and `List` casts and then require unchanged calculations, content and hash, and that a second consumer of the same shared data is unaffected. Creation inputs (`Distribution.Create` arguments, `TuningProfileDraft` lists) are copied; changing them afterwards does not reach the objects. Existing computations are untouched: the SHA-256 over the complete results of all 105 conditions under neutral / low / high inputs and every inner-zone tendency (`2ffa361a…9988`) was recorded from the unfixed code and is pinned; it is identical after the fix, as are the tuning `ContentHash` (`5b70dca7…3ea5`), the scenario seeds and the independent Python hash.
14. **Required parts of the tuning file are checked after deserialization (Codex Medium).** `System.Text.Json` only requires that a member declared `required` is *present*; an explicit `null` passes, and `"baselines": null` raised a `NullReferenceException` inside `ReadDraft`. `TuningProfileJson.ReadDraft` now checks every required object, array and array element (`tendency`; `baselines` and each row's `outcomes` / `ppm`; `modifiers`; the entries of a modifier `table`; `scenarios`; `targets`) and returns `Fixture.field_missing` with the path of the first empty part. A **missing** member and a **wrong JSON type** stay `Fixture.json_invalid` (unchanged); `table` stays optional for a linear modifier; a null *string* member is still rejected by `TuningProfile.Create` with its existing stable code (`Tuning.baseline_row_invalid`, `Tuning.modifier_invalid`, `Tuning.modifier_table_keys`, `Tuning.status_invalid`, …), so existing codes and the order of checks are preserved. Nothing catches `NullReferenceException` or substitutes a default tuning: a genuine programming error still surfaces as an exception instead of being reported as bad input.
15. **Rule for later packages.** The 3-C handoff above is unchanged. A package that adds a public collection to the model, profile, distribution or trace uses `ImmutableArray` (or another type with no writer) and adds the type to the `ImmutabilityAudit` tests. A positional record that a consumer constructs itself is the consumer's own object: only the instances the model and profile publish are guaranteed frozen. `PitchZoneModel.Zones` (3-B1, approved) still wraps a `List` in a `ReadOnlyCollection`; its list is not reachable by a cast and it is outside this fix.

## Addendum 2026-10-16 (Phase 3-D v2): the park slots, `prob-model-v2` and `tuning-virtual-proto-v2`

Nothing above is edited; v1 (model, tuning file, hash `5b70dca79ec3a3c815f741b57c4c4490e93c5bcdca19900ad452732c66d73ea5`) is unchanged and its park slots stay reserved. Decision 8's last bullet and "For 3-D" said the later package would add the park caps "under a new tuning version" and that the meaning of `Hits` needed an owner decision. Both are resolved by the owner (P1-P4, `docs/decisions/ADR-007.md` "Decisions (Park / Fielding / Advancement v2)"):

- **`Hits` is the game model's single-only weight** (P1): `park.hits` owns `single` only, as this ADR already mapped it; an external all-hits coefficient is not converted into it. The three slots keep owning disjoint outcomes.
- **A new model version was needed, not only a new tuning version.** `Reserved` is a property of the model's slot and a reserved slot's tuning must have slope 0; also the reserved input domain 1-3000 cannot carry 1,000 ppm per permille inside the combined cap [800,000, 1,250,000] because the validator checks both ends of the input range. `prob-model-v2` therefore activates the three slots over **800-1250 permille** (neutral 1000); `tuning-virtual-proto-v2` sets slope 1,000 ppm per permille and the slot range 800,000-1,250,000. The C46 domain bound (3000) is kept; a domain-valid value outside the active range is refused when the game starts.
- Every other slot, stage, condition, outcome and baseline of v2 equals v1 (tests compare them); a model and a tuning of different versions are rejected (`Tuning.model_tuning_mismatch`). The numbers are virtual; Phase 3-F judges balance.
