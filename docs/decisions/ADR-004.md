# ADR-004 — Seeded random numbers: PCG32, stream key derivation, snapshots and deterministic ids (Phase 3-A)

- Status: Proposed — Phase 3 work package 3-A implementation decisions, awaiting GPT Chat / owner review (`검토 대기`). Phase 3 as a whole is not complete and no Phase 3 Gate is claimed.
- Date: 2026-10-11 (amended the same day after two independent Codex reviews: items 13-19, which supersede the parts of items 9 and 10 they name)
- Scope: `src/StarPlayer.Simulation/Randomness/` only. No product rule changed; this implements ROADMAP §4.1 / §6.1 and §1.14 (the `game/location` stream name) inside AGENTS.md invariants. Nothing here draws a probability, resolves a pitch or changes the reducer.
- Note on sources: the task referred to a Codex "Phase 3 RNG design decision". No separate document with that name exists in the repository; the contract below is derived from ROADMAP §4.1, §6.1, §1.14 (Phase 3 work package 3-A) and SYSTEM_CONTRACTS C08, and is offered for review as such.

## Decisions

1. **Algorithm `pcg32-xsh-rr-v1`.** PCG32 XSH-RR 64/32 exactly as the PCG author's reference (`pcg_basic.c`): 64-bit state, odd 64-bit increment, multiplier `6364136223846793005`, all arithmetic unsigned and wrapping (`unchecked`).
   - Step: `state = old * 6364136223846793005 + inc`.
   - Output (from the OLD state): `xorshifted = (uint)(((old >> 18) ^ old) >> 27)`, `rot = (uint)(old >> 59)`, result = `xorshifted` rotated right by `rot` (rotation is by `(32 - rot) & 31` on the left, so `rot = 0` is the identity).
   - Seeding `(initstate, initseq)`: `state = 0; inc = (initseq << 1) | 1; step; state += initstate; step`. The two seeding steps are not draws.
   - Jump-ahead `Advance(delta)` is the standard `pcg_advance` (O(log delta)); it is used only to verify a restored snapshot.
2. **Bounded integers by rejection sampling.** `threshold = (2^32 - bound) % bound` (computed as `(0u - bound) % bound`); draw raw outputs until one is `>= threshold`; return `output % bound`. This is unbiased for every bound in `1..2^32-1`. `bound = 0` is a programming error (`ArgumentOutOfRangeException`). `bound = 1` returns 0 and **still consumes one draw** (as the reference does), so the draw count of a call never depends on whether a choice is degenerate. Every rejected output counts as a consumed draw.
3. **Draw count.** `Draws` counts raw 32-bit outputs consumed since seeding (rejected ones included, seeding steps excluded), as a non-negative `long`. It is part of every snapshot and makes consumption auditable ("this stream was used N times").
4. **Key derivation `kd1`.** A stream's generator depends only on `(master seed, context key, stream id)`:
   - input bytes: ASCII `SPRNG-kd1` || master seed (8 bytes, **big-endian**) || length (4 bytes, big-endian) + UTF-8 context key || length (4 bytes, big-endian) + UTF-8 stream canonical text `name@version`;
   - `SHA-256` of the input; `initstate` = digest bytes 0..7 and `initseq` = bytes 8..15, each an unsigned **big-endian** 64-bit integer; seed with the rule in item 1.
   - Consequences: creation order, other streams' draws, time, process, OS, culture and hash codes cannot affect a stream. The stream **version** is inside the key, so a changed consumption order (`game/location@2`) is an unrelated sequence and never silently reuses an old one.
   - Context key: 1–64 characters of letters, digits, `_ - . :` (the id alphabet), so snapshot text needs no escaping. For a game it is the game id.
5. **Stream identity `RngStreamId`.** Name = lower-case segments of `[a-z0-9_]` joined by `/` (≤ 64 characters), plus an integer version ≥ 1; canonical `name@version`. Invalid names/versions are rejected with `Rng.stream_name_invalid` / `Rng.stream_version_invalid`.
6. **Game streams (all version 1).** `game/pitch`, `game/contact`, `game/field`, `game/runner`, `game/location`, `game/ai`. Each has one purpose (documented on `GameRngStreams`); no other consumer may draw from it. Broadcast Commentary Lite and Live Match Viewer Lite have no stream here and never draw from any of these (their presentation keys are separate namespaces, ROADMAP §1.12/§1.13).
7. **`game/location` consumption rule (Pitch Zone Lite, ROADMAP §1.14).** The stream is used only for the location draw of an actual pitch, in strict game pitch order, **before** that pitch's outcome draws on the other streams, with one location draw sequence per actual pitch (an in-play pitch is one pitch, never two). The number of draws per pitch is fixed by the location model (`pzl-zones-v1`) in work packages 3-B/3-C and is recorded there; any change of the count or order requires `game/location@2`. 3-A implements no location drawing and no location probability model.
8. **`GameRandom` = the streams of one context.** Lazily creates streams; holds the master seed and context key. Single serialized writer, not thread-safe.
9. **Snapshot `rngset1`.** `GameRandomSnapshot(FormatVersion, AlgorithmVersion, KeyDerivationVersion, MasterSeed, ContextKey, Streams)` with `RngStreamSnapshot(Stream, State, Increment, Draws)` per stream that has drawn at least once (item 13), sorted by the stream's canonical text (ordinal). The master seed and context key are included so a stream that was not yet created at snapshot time still derives the same sequence after restore.
   - Canonical text: line 1 `rngset1|pcg32-xsh-rr-v1|kd1|{seed, 16 lower-case hex}|{context}`; then per stream, in order, `{name}@{version}|{state, 16 hex}|{increment, 16 hex}|{draws, decimal}`; lines joined by `\n`, no trailing newline. `StateHash` = lower-case hex SHA-256 of the UTF-8 canonical text (the "RNG hash" of ROADMAP §6 repeat-run checks).
   - `Restore` explicitly rejects: missing snapshot, unknown format / algorithm / key-derivation version, invalid context, invalid or duplicate stream, even increment, negative draws, an increment that is not the one derived for that stream (`Rng.increment_mismatch`), and a state that is not the state reached after exactly `Draws` draws from the derived start (`Rng.state_mismatch`, verified with `Advance`). A forged or corrupt snapshot therefore cannot be restored; a different master seed is rejected, not silently reseeded.
   - Phase 4 persists these fields; no SQLite mapping, table or migration exists in 3-A.
10. **Atomic scope `Atomically(work, cancellation)`.** Runs `work` on a private copy of every stream and publishes it to the original only when the result is a success and the token was not cancelled (hardened by item 16). A failure result, an exception or a cancellation leaves the original exactly unchanged; existing `RngStream` objects keep their identity and take the committed position. This is the in-memory half of "commit state, stats, RNG/counters and event receipts together"; the Application unit of work (later phases) persists the snapshot in the same transaction.
11. **Deterministic ids (`GameIds`, `GameEventIds`).** Game id = `game:{competition key}:{fixture key}` (parts of `[A-Za-z0-9_.-]`, no `:`, ≤ 64 characters total), a pure function of its parts and injective. Event id = `{game id}:e{sequence, ≥ 6 digits}` with sequence 1, 2, 3… in event order, at most `999999`; resuming passes the last issued sequence so no id repeats; exhaustion fails instead of wrapping. Id generation takes no random source, clock or content, so it can neither consume game RNG nor differ between replays. The Phase 2 reducer is unchanged and still accepts any non-empty event id string; adopting this format in the Phase 3 resolver is a 3-C decision.
12. **Forbidden inputs.** `System.Random`, time, `GetHashCode`, `Guid.NewGuid`, threads/tasks and mutable static state do not appear in `Randomness/`; a source-scan test enforces this.

## Amendments after the Codex reviews (2026-10-11)

13. **Snapshots contain only streams that have drawn (supersedes "one entry per created stream").** `Stream()` creates a stream lazily, but a stream with `Draws == 0` is at its derived start and is **omitted** from `Snapshot()`, so looking a stream up (or reading its `Draws`) can never change `StateHash` or the canonical text. A stream enters the snapshot with its exact `(state, increment, draws)` at its first draw. The `rngset1` canonical text and the golden vector (`set_vector.canonical`, `state_hash`) are byte-identical to before; no `rngset1` snapshot was ever persisted (Phase 4 does not exist yet), so the rule is part of the format's definition, not a migration.
14. **Canonical form is enforced on restore.** `Restore` rejects streams that are not in strict ordinal order of their canonical text (`Rng.stream_order_noncanonical`) and a stream entry with `Draws == 0` (`Rng.stream_unused`); nothing is silently re-sorted or normalised, because a restore that only works after changing the stored form would hide corruption. Duplicate, version, increment, draw-count and state checks are unchanged. A snapshot written by `Snapshot()` always satisfies these rules.
15. **Expected-state contract (a snapshot cannot say what it is missing).** A stored snapshot from which a consumed stream was removed is internally consistent, and a hash recomputed from it agrees with itself; `Restore(snapshot)` can therefore only be structure-only (documented limit; a regression test keeps the hazard visible). The loading contract is `Restore(snapshot, expectedStateHash)`: `expectedStateHash` is the `StateHash` of the **live** state, recorded when the state was committed (never recomputed from the stored snapshot), and the state that was actually rebuilt must hash to exactly that value, else `Rng.state_hash_mismatch` (a malformed value is `Rng.expected_hash_invalid`: 64 lower-case hex characters). A removed, added, advanced or altered stream is caught whether or not the stored snapshot is self-consistent. Failure creates nothing and changes no existing instance. **Phase 4 obligation:** write this hash in the same storage transaction as the game state and the event receipts (one commit unit) and pass it on every load. **The hash detects accidental corruption and lost or substituted parts; it is not an authentication or anti-tamper mechanism** (no secret; anyone can compute it). No hash or expectation field is added to `GameRandomSnapshot` or to the `rngset1` text.
16. **`Atomically` guarantee and hardening.** The guarantee is limited to the **in-memory RNG state of that one `GameRandom`**. While a scope runs, the original is locked: drawing from it or from any previously obtained `RngStream`, `Stream()` on it, and starting another scope on it or on the working copy all throw `InvalidOperationException` before anything changes (reading `Draws` and `Snapshot()` stay allowed and show the last committed state). The copy shares no mutable object with the original (generators are cloned), and after the scope ends - normally, by failure, exception or cancellation - the copy is closed: a stream or copy that escaped can no longer draw or start a scope. The lock is always released (`finally`). Nothing else is covered: event-id counters, `GameReducer`/`GameState`, event receipts, other objects and external side effects stay outside, and publication happens when the work returns, **not after a durable commit**. The combined unit is the Phase 3-C/4 contract below.
17. **Draw limit.** `Draws` is a `long`; `NextUInt32` throws `InvalidOperationException` at `long.MaxValue` **before** the state changes, so the counter cannot wrap. `NextBounded` restores state and counter to their pre-call values if the limit is hit while skipping rejected outputs. `Advance` validates before changing anything: a delta above `long.MaxValue` is `ArgumentOutOfRangeException`, a delta above the remaining allowance is `InvalidOperationException`. Outputs for all valid draws are unchanged (golden vectors identical).
18. **Culture and threads.** `RngStreamId.Canonical` formats the version with `InvariantCulture` (tested under ar-SA, fa-IR, th-TH, tr-TR; the output was already invariant for positive integers, the call is now explicit). `GameRandom`, its streams and scopes support a **single serialized writer only**; concurrent use is neither supported nor detected (a probe showed lost draw counts under four threads).
19. **Snapshot version and API compatibility.** `rngset1`, `pcg32-xsh-rr-v1`, `kd1` and the golden vectors are unchanged; the public API only gains `Restore(snapshot, expectedStateHash)`. Behaviour changes that could affect a caller: `Snapshot()` omits unused streams; `Restore` rejects non-canonical order and unused entries; `Stream()` and draws throw while a scope runs; `RngStream` has an owner (internal constructor); the draw limit throws. No 3-A consumer and no persisted data exist.

### Handoff to Phase 3-C / Phase 4 (recorded, not implemented)

1. **Joint atomicity of the event-id sequence and the reducer result.** `GameEventIds.Next()` advances immediately and is outside `Atomically`; a failed attempt burns ids, so a retried step would differ from a clean run. Derive ids from committed state (for example the applied-event count) or roll the counter back with the RNG as one unit.
2. **One success unit for game state, event receipts and RNG** (resolver output, `GameReducer.Apply` result, ids, receipts and the RNG snapshot succeed or fail together).
3. **Publish memory only after the durable commit.** `Atomically` publishes on return. The upper layer must hold the working result, write state + receipts + RNG snapshot + `StateHash` in one storage transaction, and only then make the new in-memory state current (for example a commit callback, or a fork/publish pair with a revision check); on a failed commit the memory must stay at the last committed state.
4. **`game/location` real consumption order and the probability scale** (draws per pitch, location before outcome draws, an integer fixed-denominator scale for `NextBounded`) belong to 3-B/3-C.
5. **New `ef2` events and replay** (location-carrying events, receipts by version, new JSON format) belong to 3-C; `ef1` stays untouched.

## Out of scope in 3-A (deliberately not built)

Probability tables or a unit-interval/`double` draw (the resolver can use `NextBounded` with a fixed-denominator integer scale; the choice belongs to 3-B), location drawing, any `ef1`/`ef2` event or fingerprint change, pitcher AI, framing, persistence.

## Verification

Golden vectors are not produced by the C# code. `tests/Fixtures/generator/generate_rng_golden.py` is an independent Python implementation of the reference; before writing anything it asserts the values **published by the PCG author** (seed 42 / sequence 54: the six 32-bit values `a15c02b7 7b47f409 ba1d3330 83d2f293 bfa4784b cbed606e` and the 33 bounded dice rolls after 71 draws). The same published values are typed directly into `Pcg32Tests`. The remaining vectors (extreme seeds, bounded values with rejection, jump-ahead, `kd1` keys, an `rngset1` set with canonical text and hash) come from the Python script into `tests/Fixtures/phase3a_rng_golden.json`. Limits: the Python script and the C# code share one author's reading of `kd1`/`rngset1` (only the PCG parts and SHA-256 are externally anchored); no C compiler was available to run the upstream C demo directly. Results: `docs/reports/PHASE_3A_REPORT.md`.
